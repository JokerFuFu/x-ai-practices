# 给工程 Agent 分层反馈,别只报一个总分

> **原作者说法**:GLM-5.3 驱动的 Infra Agent 参与优化 GLM-5.3-Flash 的生产推理系统。团队发现 Agent 卡住时,常不是不会写代码,而是不知道性能为什么变差;因此给它可调用的正确性、系统行为、性能三层反馈。目标、反馈环境与高风险改动审查仍由人负责。作者称端到端吞吐量提升 3.2 倍,这属于团队披露,未获独立复现。
>
> 下文的通用步骤、验收清单与适用边界是本仓库的工程化整理,不是原作者逐字给出的通用配方。

## 要解决什么问题

只给 Agent 一个最终吞吐量或测试总分,它知道“坏了”,却不知道哪一层出错。若完整基准一次要跑几小时,盲目试错又贵又慢。人类资深工程师脑中的排障顺序,需要变成 Agent 能读取、能调用、能客观比较的接口。

## 今天就能照做的五步

1. **固定任务与底线。** 写清目标指标、正确性红线、基线环境和允许修改的范围;高风险路径单独审批。
2. **加正确性反馈。** 每次候选改动先跑最短的确定性检查,记录输入、输出、容差和原始退出状态。正确性不过关,不比较速度。
3. **加系统行为反馈。** 给 Agent 看执行时间线、分层耗时、资源占用与关键调用边界,让“慢了 20%”能定位到具体阶段或假设。
4. **加条件化性能反馈。** 用小型基准在相同负载、硬件和配置下比较候选方案;记录何种条件下胜出,而非只报一个峰值。
5. **先小范围验证,再由人审查上线。** Agent 给出改动、证据与回退方法;人复查风险,完整回归和生产流量验证仍是独立闸门。

三类反馈都应尽量**局部、便宜、客观可核验**。测量接口本身也要版本化,否则 Agent 可能学会优化错误指标。

## 从产物验证升级到约束工程

补充作者把最小自治闭环拆成两层：第一层让 Agent 真正运行产物并给出证据；第二层把反复出现的错误变成代码库中的硬约束。作者将代码库视为 Agent 的长期记忆，因为 Agent 会优先延续已经存在的结构和模式。这是个人工程实践，未经独立复现。

### 第一层：让 Agent 交付可复核的运行证据

1. **按真实入口验证。** CLI 就执行命令，API 就发送请求，UI 就在浏览器或设备上完成关键路径；只跑类型检查或单元测试不等于功能已生效。
2. **证据要比整份 diff 更容易审。** 保存退出码、响应片段、截图、短视频或状态机轨迹，让审阅者直接判断结果是否正确、是否符合意图。
3. **验证器与实现分离。** 实现 Agent 不能自己改通过条件；checker、黄金输入和关键断言由独立文件或流程控制。
4. **明确验证近似的边界。** 截图能证明一个视口，不能证明响应式页面；一次成功请求不能证明并发安全。每份证据标明未覆盖项。

### 第二层：把重复错误写进代码库

1. **记录反复出现的错误模式。** 包含触发条件、错误表现、为什么现有测试没拦住，以及理想的禁止条件。
2. **优先升级成机制。** 能用类型系统、编译器诊断、lint、schema、权限和测试表达的约束，不留在易被忽略的提示词里。
3. **缩小架构搜索空间。** 提供少量高质量 primitive、明确 API 和统一数据流，让错误实现不是“不推荐”，而是难以或无法表达。
4. **用负向样例证明约束生效。** 放入过去真实失败的最小复现，确认错误代码会在最便宜的阶段被拒绝，并且不会误伤合法路径。
5. **持续观察再收紧。** 新 PR 暴露的新反模式继续进入约束候选；不要一次性加入大量规则，导致团队无法定位是哪条约束造成回归。

### 适用边界

- UI、分布式系统和开放式研究很难被单一 checker 完整证明；验证提供置信度，不提供绝对真理。
- 过强类型和过窄框架可能压制合理的新设计。约束应来自重复证据，并保留经过审查的逃生口。
- 代码库是共享记忆，也可能保存旧时代的坏模式。迁移约束前先确认它仍适用于当前架构和模型。
- 截图、日志和视频可能包含密钥、个人信息或内部数据；保存与分享前必须脱敏，并设置保留期限。

## 作者实跑中的三类定位

- **正确性:**长上下文并行路径中,链式状态矩阵合并导致精度漂移;作者称修复已合并到 Flash Linear Attention。
- **系统行为:**KV 传输没有与 DeepEP dispatch 重叠,排查跨 Python/C++ 边界后发现节点内路径未释放 GIL;作者称修复后相关开销从超过 30% 降到不足 1%。
- **性能:**某解码内核重复进行四次归一化;重组后作者称内核加速 1.71 倍。

这些案例展示的是如何定位问题,不是保证别的系统也能得到相同增益。

## 验收清单

- 复现同一负载时,基线和候选使用同一硬件、配置与测量口径。
- 保留正确性结果、时间线/微基准、完整端到端回归三份证据。
- 记录失败候选及原因,避免 Agent 重复探索同一路径。
- 高风险变更有人工审查和明确回滚点。
- 过去重复出现的错误已有负向样例，并由类型、lint、schema 或独立 checker 在早期阶段拦截。

## 适用边界

适合性能、可靠性或成本能被分层测量的工程任务,尤其适合完整回归很慢、但局部检查能快速提供信号的系统。不适合目标本身无法操作化、缺少可信基线、测试环境与生产差异极大,或变更未经授权就可能影响真实用户的场景。

作者没有声称“递归自我改进已经实现”;这些性能数字来自其团队披露,不是独立基准。分层反馈能帮助 Agent 排障,不能代替人工设定目标、检查测试是否有效、批准高风险上线。
