## 问题

给 AI 改稿的标准姿势是在 chat 里描述:

> 第三段把 X 改成 Y。第三张卡片和第一张重复了,删掉。CTA 再重写一遍。

这句话要经过四道转换:你心里想的 → 你写出的描述 → agent 的理解 → agent 改出的结果。然后你还得**逐条回去核对它有没有理解对**。稿子越长、页面越多,核对成本涨得越快,最后你花在验收上的时间超过自己动手改。

## 核心机制:把反馈从「描述」降级成「已完成的编辑」

这个回环里最关键的一条设计,在它 SKILL.md 的规则里写得很直白:

> **`edits` 是用户已经改好的东西。`after` 是他们的原话——原样搬过去,永远不要回退。**

也就是说,人不再**描述**要改什么,而是**直接改好**;agent 拿到的不是指令,是既成事实,它唯一的活是把这个事实**搬运**到源文件里(渲染的 HTML → MDX/Markdown 源)。

「理解」这一环被整个删掉了,失真也就没了。

批注(`comments`)才走原来的老路——那是真正需要 agent 判断的部分。**能自己一秒改完的直接改,需要商量的才留言**,两类反馈走两条通道,这是它比「截图丢给 AI」高明的地方。

配套的几条设计同样值得抄:

- **锚定用 prefix/quote/suffix 三段文本,不用行号。** 审的是渲染后的产物,没有行号可言,而且文件随时在变。三段锚定在文本漂移后仍能定位。
- **`kind: "url"` 必须改源,绝不把 HTTP 响应写回项目。** 审 localhost 页面时,agent 得自己找到对应的 MDX/TSX/模板去改。这条规则不写死,agent 迟早会把渲染结果覆盖进源码。
- **`kind: "moved"` 只搬位置不改内容**,用 `moved_after`/`moved_before` 两个邻居描述新位置——比传坐标或索引稳。
- **「不要回复。这里没有聊天。」** 人看到的是保存后自动刷新的页面。省掉了 agent 那段「我已为您修改了以下 5 处……」的复述——那段话除了消耗上下文和你的注意力之外没有任何作用。

## 为什么它是流程改动,不只是个工具

真正让「人在回路」落地的是这条:

```sh
human-review poll <target> --timeout 600
```

**这是阻塞的,而且 SKILL.md 明确要求 agent 不许在等待期间结束回合。**

差别很大。指望人「事后想起来去看一眼」,回路基本不会闭合;而把阻塞式等待嵌进 agent 的执行流,人的审阅就成了任务完成的**必经步骤**。反馈到达 → 应用 → 再 `--ack` 继续等,直到人说结束。

反馈状态是落盘的,poll 进程死了也不丢;`status` 子命令可以非阻塞地问「有没有攒着的反馈」,适合放在新回合开头。

## 怎么用

装(**别照 README 用 npx,见下面的坑**):

```bash
npm i -g "github:petergyang/human-review#v0.6.0" && human-review setup --global
```

`setup --global` 只做一件事:往 `~/.claude/`、`~/.codex/`、`~/.agents/` 三处的 `skills/human-review/SKILL.md` 写同一份说明书,教 agent 这套回环怎么走。没有账号、没有云服务、没有 API key,server 跑在本机。

用:

```bash
human-review path/to/file.html        # 或 .md,或 http://localhost:3000/xxx
```

浏览器打开后直接改字、划词批注、拖块换位、⌘K 加链接、粘贴图片(自动存到同级 `assets/`),点 Send 一次性发回。

**写产物时预埋区块名**,反馈回来就是有意义的标签而不是 DOM 猜出来的名字:

```html
<p data-block="问题陈述">…</p>
<div data-container="指标卡片">…</div>
```

`data-container` 还会让整块变成可点击的批注目标。这一步花几秒,回收的是每轮反馈的可读性。

## 安装坑(实测)

**npm 上的版本落后 GitHub 三周。** 实测 2026-08-09:npm `latest` 停在 **0.3.0**(2026-08-01),GitHub 已发到 **v0.6.0**(2026-08-08)。发布流水线是 `on: release: published` 触发的,v0.5.0/v0.6.0 的 Release 都发了但 npm 没跟上——发布 workflow 挂了。

后果是 README、SKILL.md 里那些 `npx -y human-review` 全部拉到 0.3.0,而**推文里新宣传的功能一个都不在里面**:实测 0.3.0 的 `src/` 里搜不到 ⌘K 链接、列表快捷键、拖拽、块移动(`moved_after`)的任何实现。0.3.0 的包里甚至还是小写的 `skill.md`,而 `setup.js` 读的是 `SKILL.md`——macOS 默认大小写不敏感才侥幸没崩,换到大小写敏感的文件系统上直接 ENOENT。

**修法是装 GitHub tag,而且顺序不能反:**

```bash
npm i -g "github:petergyang/human-review#v0.6.0"   # 先让真 binary 进 PATH
human-review setup --global                        # 再写 SKILL.md
```

`setup.js` 里的 `invocation()` 会探测 PATH 上有没有 `human-review`,据此决定写进 SKILL.md 的是裸命令还是 `npx -y human-review`——它还专门做了排除,不把 npx 自己的临时缓存路径当数(注释里写了这个坑:`npx ... setup --global` 期间 `which` 会误报成功,写出的裸命令在 npx 退出后就失效)。所以**先全局装、再 setup**,SKILL.md 里落的才是裸 `human-review`,agent 每次调用少一次 npx 解析,也彻底绕开 npm 的旧版本。

装反了就再跑一次 `setup --global` 覆盖。

## 增补：先换输出格式，再继续解释

> **原作者说法**：理解模型输出时，他会先要求更受控的写法，例如 ASD-STE100，或只采用其中约 80% 的约束；关系复杂时改要图；需要探索时让模型输出交互 HTML；最看好的形式是针对任意主题生成定制解释视频。

这不是“越多媒体越好”，而是**当前格式已经让读者费力时，先换一种更适合认知任务的载体**：

1. **事实和步骤先用受控文字。** 限制句长、术语和歧义，要求一条句子只承担一个动作或结论。ASD-STE100 是可选参考，不必机械照搬航空维修文体。
2. **结构关系改用图。** 流程、层级、状态变化或组件依赖超过三项时，用最小图解替代连续段落；图中的每个节点必须能回到正文证据。
3. **需要比较与试探时用交互 HTML。** 把参数、筛选、前后状态和“如果改变 X 会怎样”做成可操作界面；默认值、单位和数据来源必须可见。
4. **需要节奏与空间变化时再做视频。** 视频适合过程演示和概念建立，但应先有脚本、分镜和静帧验收，避免在昂贵渲染后才发现事实或结构错误。
5. **每次升级格式都保留降级版本。** 图要有文字说明，交互页要有静态摘要，视频要有字幕或逐字稿，保证搜索、引用、无障碍与低带宽使用。
6. **最终验收“是否更容易理解”。** 让目标读者复述关键结论或完成一个小任务；不能只用画面精致度、动画数量或生成速度作为通过标准。

### 适用边界

- 受控语言可降低歧义，但可能牺牲语气、叙事和专业术语精度；面向专家时应保留必要词汇并给定义。
- 图、网页和视频会引入布局、前端、性能、版权与无障碍成本。一个清楚的短答案已经够用时，不要升级格式。
- 模型生成的图像与视频可能把错误“画得更可信”。事实、数字和因果应在进入视觉制作前锁定，并在成品中抽查。
- 交互 HTML 适合解释和探索，不替代生产应用的安全、兼容、数据质量与业务测试。

## 增补:3D 页面先明确素材,再审阅真实交互

> **原作者说法**:Meng To 在自己的 three.js 页面制作中观察到,Fable 5.1 更能理解复杂设计要求,但不指定图片时仍会生成泛化插画;人物、狗等复杂 3D 主体需要外部模型辅助。他还需继续调整纹理、光照和建模细节,并亲自修正元素重叠、留白与滚动行为。生成更快的同时,Token 也消耗得更快。这是个人使用经验,不是跨模型评测结论。

这条经验给前文的产物审阅补了一个具体方向:**反馈不只针对文字,还应覆盖素材、空间关系和交互。** 看起来漂亮的首页截图,不能证明滚动、遮挡和模型细节都可用。

### 可执行流程

*下面的步骤是本仓库对原帖观察的工程化整理,不是原帖逐字指令。*

1. **先固定素材范围。** 给出允许使用的图片与模型,并说明主体、风格和不可改变的特征。遇到复杂人物或动物,先比较已有资产与生成资产,不要默认让模型从零造型。
2. **生成一个可检查的版本。** 留下模型与 effort、主要素材、已知限制和本轮消耗。先明确哪里可以妥协,再继续迭代。
3. **把视觉反馈拆开。** 分别记录纹理、光照、形体、小细节、元素遮挡和留白问题,避免只说“再精致一点”。
4. **在真实页面里测试交互。** 滚动、窗口缩放、关键控件和不同视口分别检查。每个问题留下可定位截图或操作步骤,让下一轮修改有明确目标。
5. **改源后重新验收。** 检查修改是否解决原问题、是否引入新遮挡或滚动异常;不要把一张新截图或代码生成完成当作通过。

### 适用边界

- 适合视觉导向的网页和 3D 场景;对账务、权限和后端正确性,仍应依赖测试与业务判据。
- 外部模型可以改善主体造型,但不自动解决加载性能、响应式布局、无障碍和交互问题。
- 原作者使用的某个资产工具不是强制依赖;先核验授权、可用格式和项目约束,再决定是否采用。
- “生成更快”不等于“交付更便宜”。在开始前约定迭代预算与停止条件,到达预算后列出未解决项,不能靠无限重跑消耗掉它们。
- 这是一位设计实践者对一个模型版本的观察;不能推出该模型在所有视觉任务上更好。

## 增补：动效先选变体，再做生产检查

> **原作者说法**：他的动画与交互工作已经基本不直接改代码。做法是先用 `/prototype` 生成几个方向，并让 `/animate` 处理缓动和时间；选中一个变体后，继续让 Agent 修改细节；最后运行 `/prep-for-prod`，检查性能、无障碍与移动端。命令名来自他的工具配置，不是通用标准。

可迁移的不是三条斜杠命令，而是**探索、收敛、放行分成三段**：

1. **原型阶段只比较方向。** 同一目标生成 3—5 个差异足够大的动效版本，固定内容与布局，主要比较节奏、层级、反馈和空间运动。此时不急着优化代码。
2. **选中一个方向后再改细节。** 每轮只改一类问题，例如 easing、duration、stagger、进入/退出关系或操作反馈；浏览器里实际触发，不靠静态截图判断。
3. **把“喜欢”翻译成理由。** 记录为什么选这个版本：是否强化层级、是否让状态变化更清楚、是否减少等待感。下次 Agent 才能复用判断，不只是复用数值。
4. **生产检查单独运行。** 至少覆盖主线程与帧率、`prefers-reduced-motion`、键盘和焦点、触屏尺寸、低性能设备，以及动画失败时内容是否仍可用。
5. **最终验收真实路径。** 从用户操作开始走完整流程，检查快速重复点击、路由切换、中途取消、窗口缩放和页面恢复，不把单次播放顺滑当成交付。

### 适用边界

- 适合微交互、页面转场和可通过浏览器反复触发的动效；复杂 3D、视频渲染与物理模拟需要专门性能工具和素材管线。
- 生成多个变体会放大审阅成本。没有明确选择维度时，五个版本只会变成五份主观争论。
- Agent 能调整参数，不代表它理解品牌节奏。关键页面仍需设计负责人确认，并把理由沉淀为 design token 或 motion guideline。
- `/prep-for-prod` 一类检查不能替代真实设备。自动检查通过后仍要在低端设备、触屏和 reduced-motion 设置下试用。
- 无障碍不是“关掉所有动画”。对理解状态有帮助的动效可以保留，但必须有低运动替代，并避免闪烁、眩晕和不可中断的长动画。

## 增补：动效视频先定参考与静帧，再开始渲染

> **原作者说法**：作者发现“一个提示词做专业动效”并不可靠，于是复盘了一批效果较好的案例，并在自己的流程里拆成六步：先给 1—2 条参考视频，再用 HyperFrames 或 Remotion 代码化渲染，引入真实 UI 组件和品牌素材，要求三版分镜，逐场景检查静帧，最后用明确的镜头语言迭代。他认为参考与上下文决定了成片是否摆脱模型默认的居中标题、渐变背景和统一淡入风格。

下面保留这条流程的结构，但不绑定原帖中的具体工具：

1. **先选 1—2 条参考，只说明要迁移的维度。** 分别标出节奏、字体、构图、转场和镜头运动；不要只说“照这个做”，也不要让 Agent 猜哪些元素可复用。
2. **让视频进入可重复渲染的代码管线。** 每个场景、时间点和组件都应可定位修改并重新渲染，避免把最终流程建立在录屏或整段重生成上。
3. **一次性提供品牌与真实产品素材。** 包括颜色、字体、标志、产品截图和要表达的主线。缺少这些约束时，Agent 会用默认 UI 和占位内容补空白。
4. **先要三版分镜，不先要三条成片。** 用同一内容比较三种叙事方向，选定一版后再继续；探索阶段的目标是做选择，不是打磨动画参数。
5. **逐场景验静帧。** 动画前先检查信息、布局、品牌和素材是否正确。静帧修改成本低，也能防止错误在后续转场和渲染中扩散。
6. **用导演语言给单变量反馈。** 例如“缩放速度改成 0.7×”“这里硬切”“镜头推进到按钮”，每轮只改节奏、镜头或转场中的一类问题，并重新走完整播放路径。

### 适用边界

- 适合产品演示、解释型短片和可由组件组成的 motion graphics；人物表演、写实镜头与复杂物理效果仍需专门素材和制作工具。
- 参考视频用于明确节奏与构图，不等于可以复制受版权或品牌保护的画面、音乐、字体和角色。对外发布前要单独核授权。
- HyperFrames、Remotion 与组件库只是原作者的选择，不是流程成立的必要条件；任何能稳定定位场景并重复渲染的管线都可以替代。
- 代码化渲染提高可修改性，不自动保证帧率、编码质量、字幕可读性、无障碍或移动端表现。最终仍要在目标设备和平台验收。
- 三版分镜会增加探索成本。先约定选择标准和停止点；没有明确方向时继续生成更多变体，只会把决策推迟。

## 适用与不适用

**适合**:方案/规划/报告/newsletter 草稿、落地页、幻灯片、localhost 应用——凡是**产物本身是给人读的、且你会想动手改几个字**的东西。文档越长、页面越多,相对 chat 描述的优势越大。

**不适合**:后端代码、配置、数据管线。这类产物没有「渲染后的样子」可审,该走 diff 和测试。也不适合你**根本不想自己动手**、只想说一句「你看着办」的场景——那还是直接在 chat 里说更快。

**注意**:Markdown 文件是渲染后审的,工具本身**从不写 Markdown 源**,所有改动都得 agent 翻译回 Markdown 语法落到源文件。如果 agent 偷懒直接写渲染后的 HTML,源文件就毁了——这条依赖 agent 守规矩,SKILL.md 写了,但值得你第一次用的时候盯一眼。
