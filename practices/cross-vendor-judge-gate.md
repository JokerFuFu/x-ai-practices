# 异构终审闸门:让另一家供应商的模型来打分

> **出处** — [@EXM7777](https://x.com/EXM7777/status/2083914725419806857) · 采集于 2026-08-04
> **原作者说法**:研究型 agent 的完整环是「起研究计划 → 跑一次 → 人工审输出 → 删掉没用的、围绕缺口重写计划 → 再跑一次」,中间用一批子 agent 交叉验证结论,**最后由另一家供应商的模型做质量评分,低分打回**。
> 原推同时在推荐若干检索工具,那部分是软文,本文只取工作流。以下「工程化落地」小节为本仓库补充,非原作者内容。

## 它要解决的问题

模型自评有个绕不过去的缺陷:**同源偏见**。同一个模型(哪怕换个系统提示词扮演「严格的审稿人」)在评自己的产出时,系统性盲点原样保留——它认为重要的东西还是重要,它习惯性忽略的地方还是被忽略,它偏爱的措辞读起来还是顺眼。

换一家供应商的模型来评,价值不在于「更聪明」,而在于**失效模式不同**。A 家会漏的那类错误,B 家不一定漏。这是冗余,不是升级。

对应的推论也很重要:**如果两个模型依赖的是同一份被污染的输入**(比如同一份抓错了的取数结果),异构评审防不住——那属于共模故障,得回去修数据源。

## 三个必要条件

这套东西很容易退化成「叫来第二个模型说两句,听着有理就改」。要让它真是**闸门**,三个条件缺一不可:

### 1. 评审方只拿产物 + 原始素材,拿不到生成方的推理过程

这是异构评审唯一的价值来源。把「我为什么这么写」一并塞给评审模型,它会被说服——你只是把同源偏见换成了锚定效应,钱照花,收益归零。

评审方的输入应当**严格限定为三样**:原始素材(取数结果 / diff / 需求文档)、固定的判据清单、待评的产物。

### 2. 判据是固定清单,评审方只能填判定、不能改判据

评审 agent 只允许把每条判据的 `passes` 翻成 true/false。**判据本身要改必须人点头。**

理由很直接:让被评方或评审方拥有修改判据的权力,等于允许它给自己放水(reward hacking)。这条在自动化循环里尤其致命——没有人在环的时候,判据是唯一的锚。

### 3. 低于阈值的后果是写死的,不是「人看着办」

否则它就是一条建议,不是闸门。后果必须提前定义,且**有明确的轮次上限**。

## 工程化落地

### verdict schema

评审方只输出结构化判定,不输出散文:

```json
{
  "verdict": "pass | revise | block",
  "score": 0,
  "checked": [
    { "id": "E1", "passes": true, "note": "" }
  ],
  "blocking": [
    {
      "quote": "产物中的原句",
      "problem": "口径矛盾 / 无出处 / 与素材不符",
      "evidence": "素材中的对应片段,或明确说明素材里找不到"
    }
  ]
}
```

`blocking` 里必须带 **evidence**。只说「这里存疑」而给不出素材依据的条目,应当被当作噪音丢弃——否则评审方会倾向于多提意见来显得尽职。

### 闸门规则

```
blocking 非空,或 score < 阈值
    → 改稿
    → 重评一次
    → 仍不过:照常交付,但在产物开头插入「未通过交叉核验」标记,
              并把 blocking 列表推给人工判断

最多两轮。
```

**轮次上限不是可选项。** 自动化循环里,「改到过为止」是最典型的空转烧钱模式:评审方每轮都能挑出新的东西,而产物在第三轮之后基本不再变好。

### 关键约束:别让裁判写稿

给评审方的任务描述里必须明确:

```
只读,不要改任何文件。
按 <判据清单路径> 逐条核验 <产物路径>,素材是 <素材路径>。
只输出 verdict JSON,不要给修改建议,不要重写内容。
```

最后一句最容易被省略,但它是整套机制的命门。**裁判一旦开始写稿,就变成了第二个作者**——你会不自觉地采纳它的措辞和结构,两个模型的产出混在一起,异构性当场消失。让它只说「这里错了、证据是这个」,改由原作者改。

## 落点一:研究型 agent 的事实闸门

这是原作者的原始场景,也是收益最高的落点——**因为研究型产出通常没人复核**。

典型失效模式(这些恰恰都是生成方自己发现不了的):

- 把厂商自述当既成事实转述
- 同一事实的多个口径,替读者二选一而不是并列标注
- 引用的作者署名错误(转推场景尤其高发:署了转推者而非原作者)
- 跨日重复(昨天已经报过的内容今天又来一遍)
- 「今日无新增」类结论其实是漏读,不是真的没有

判据清单示例(`eval.md`,**判据只增不删不改**):

```
E1  每条断言都能在原始素材里定位到具体出处
E2  数字(参数量/跑分/价格/时长)与原文一致;来自厂商自述的,正文有「未核实」标注
E3  署名正确:转推条目署原作者而非转推者
E4  与上一期产出无重复条目(按素材 id 比对)
E5  同一事实的多个口径并列标注,没有替读者二选一
E6  引用链接指向的作者与正文引述的作者一致
E7  「无新增」类结论有对应的空素材结果支撑,不是漏读
```

这类判据的共同点:**都是可以拿素材直接对照验证的**,不涉及品味判断。评审模型在事实核对上比在「写得好不好」上可靠得多,判据清单应当尽量往前者靠。

## 落点二:代码合入前的对抗性评审

许多 agent 工具链里已经有「让另一家模型 review 代码」的现成命令。差别在于:那些通常是**你想起来才跑**,跑完看一眼就算。补两件事就成闸门:

- **绑到合入动作上**——ship / merge / deploy 之前强制跑一次,输入是 diff + 该功能的验收清单,**不给它实现思路**。
- **给它明确的拒绝权,但不给它修改权**——只允许输出 `block / revise / pass` 三态 + 阻塞项,不允许直接改代码。阻塞项未清空不得合入。

### 对称规则:谁写的,谁不判

比任何评分标准都管用的一条:

- Codex(或任何 B 家模型)实现 → A 家终审
- A 家实现 → B 家终审

许多人只做了一半——把活派给另一家模型之后,自己去验证它的产出,却从不让它验证自己的产出。**冗余是双向的才有意义。**

## 什么时候别用

- **有确定性验证手段的地方,不要用模型当裁判。** 测试能跑就跑测试,脚本能校验就写脚本。交叉评审只用在没有 ground truth、只能靠判断的场合(研究结论、内容事实性、设计取舍)。
- **高频轻量任务不值得。** 每次终审都是一次完整的模型调用。一天跑一两次的产出适合,一天跑几十次的不适合。
- **共模故障防不住。** 两个模型吃同一份错数据,会一起错。评审通过不等于素材可信。
- **纯风格判断上收益很低。** 「哪个措辞更好」这类问题,换一家模型只是换一种偏好,不是换一种正确性。

## 一句话总结

异构终审的本质是**用不同的失效模式做冗余**,不是找一个更聪明的裁判。它成立的前提是:裁判看不到你的推理、改不了判据、而且它的判定会真的挡住东西。三条里少任何一条,你花的钱都只买到了一个心理安慰。
