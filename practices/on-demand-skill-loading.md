# 把指令切成按需加载的 skill

> **出处** — [@0xkkai](https://x.com/0xkkai/status/2083928030930469315) · 采集于 2026-08-04
> **原作者说法**:在 skills 目录下放一个文件夹,里面一份 `SKILL.md` 写清「用户问到 X 时触发我」;启动时只读这行描述,真问到 X 才把整份说明、脚本、示例拉进来。这样上下文默认是空的,一个助手表现得像 30 个专家,而你不用手动切换。
> 个人经验,未经官方确认。原推末尾带引流外链,本文只取正文中可照做的部分。

## 它替代的是什么

**越写越长的全局提示词。** 那种文件的典型病症:

- 每次会话都全量加载,不管这次用不用得上——上下文被常年占用
- 不同领域的规则互相干扰(写作口吻的要求会污染改代码时的判断)
- 长到没人敢删,只敢加;半年后没人知道哪几条还生效

按需加载把这件事反过来:**默认什么都不加载,由触发条件决定拉什么进来。**

## 结构

```
skills/
  writing-tone/
    SKILL.md        # 只写:我是干什么的、什么时候该用我
    examples.md     # 触发后才加载
  repo-conventions/
    SKILL.md
    checklist.md
  expense-flow/
    SKILL.md
    scripts/
```

关键在 `SKILL.md` 的**描述行**——它是唯一常驻上下文的部分,所以要写成**触发条件**而不是内容摘要:

- 不好:「本文档描述了写作风格规范」(这不告诉模型什么时候该读)
- 好:「用户要起草对外文案、公告、邮件时使用;润色已有文本时也用」

描述写得含糊,skill 就永远不会被触发;写得太宽,就等于又变回了全局提示词。**这一行的质量决定整套机制成不成立。**

## 怎么切

原作者给的三个切分维度很实用:

| 维度 | 例子 | 触发时机 |
|---|---|---|
| **按输出类型** | 写作口吻 | 只在起草/润色时 |
| **按代码库** | 某个仓库的约定 | 只在改那个 repo 时 |
| **按业务流程** | 报销/发票流程 | 提到发票才加载 |

判断标准很简单:**如果两组规则从不在同一个任务里同时用到,它们就该是两个 skill。**

## 边界

- **切太碎会有反效果**——十几个 skill 的描述行加起来,又成了一份常驻长文。合并那些总是一起触发的。
- **真正全局的东西留在全局**(比如「所有回复用中文」),别硬塞进 skill。
- 具体的目录位置和加载机制**因工具而异**,上面的结构是通用形状,落地时按你用的 agent 工具的约定来。
