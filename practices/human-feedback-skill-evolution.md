# 让 Skill 从人类反馈中进化,而不是让它自己瞎改

> **出处** — [Warp × Anthropic 官方案例](https://www.anthropic.com/webinars/how-warp-builds-self-improving-agents-on-claude) · [@dotey 的实践拆解与个人实验](https://x.com/dotey/status/2093539751127040157) · [WikiSkill 论文](https://arxiv.org/abs/2608.27454) · [轨迹投毒研究](https://arxiv.org/abs/2608.05563) · 采集于 2026-08-31

> **原作者说法**:Warp 没让模型凭自己的感觉反复重写 Skill,而是让代码审查 Agent 学习工程师在 PR 里的自然反馈:基础 Skill 负责审查,改进 Skill 收集人类对审查结果的评论,从中提出下一版 Skill 更新。@dotey 也记录了两个相反的个人实验:反编译 Skill 在遇到新场景后持续更新,效果会改善但文件越长;写作 Skill 因缺少统一标准,经常越改越差。他归纳的关键做法是写原则与原因、在原工作流里低摩擦收反馈、限制谁的反馈有权影响更新,并始终保留人工审核。

下面「四层结构」「更新闸门」「投毒边界」与检查清单是本仓库结合 WikiSkill 和安全研究补充的工程化落地,不是任一原作者的逐字方案。论文结果均未在本仓库独立复现。

## 它要解决的问题

固定 Skill 会逐渐过时,但“让 Agent 自己改自己的 Skill”并不天然更好。

一次运行失败后,最直接的做法是把失败轨迹整段塞进 Skill。很快会出现三个问题:

- **文件只增不减**:例外、补丁和旧场景不断堆积,每次调用都要支付更多上下文。
- **把偶然当规律**:某次任务的局部修补被提升成全局规则,在其他任务上反而退化。
- **错误经验升格为长期指令**:运行轨迹本来是不可信证据,一旦写进 Skill,后续 Agent 会把它当成可信规则。

真正需要的不是“自我改写”,而是一条有来源、有验证、有批准、有回滚的**经验晋升流水线**。

## 正确的形状:执行和改进分开

```
基础 Skill 执行任务
        ↓
人类在原工作流中评论结果
        ↓
反馈收集器记录来源、任务和理由
        ↓
持久 Wiki 归纳可复用经验
        ↓
改进 Skill 生成最小候选 diff
        ↓
留出集 / CI / 人工评审
        ↓
批准后发布,失败则回滚
```

最重要的分工是:**执行 Skill 不直接修改自己;改进 Skill 也不能直接发布修改。**

## 四层结构

### 1. 原始轨迹:只读证据

保存任务输入、工具调用、输出、检查结果和人类评论。它回答“当时发生了什么”,不回答“以后都该怎么做”。

轨迹应该不可变,并带上:

- 任务与代码版本
- 执行模型、Skill 版本和工具版本
- 反馈人的身份或角色
- 机器检查结果
- 最终是否被接受

### 2. 持久 Wiki:累积理解

Wiki 把多次轨迹里的共性提炼成可查证的知识,例如:

- 某类失败为什么反复发生
- 哪些条件下旧规则不适用
- 什么证据支持这条经验
- 是否存在互相冲突的反馈

WikiSkill 的核心贡献就是把**原始经验、累积知识、可执行 Skill**分开。战术可以回滚,对失败原因的理解不能随补丁一起丢掉。

### 3. 可执行 Skill:短而稳定

Skill 只保留当前任务真正要执行的原则、步骤和检查。详细案例、长解释和脚本放在按需资源里,不要一次性塞进常驻文件。

优先写:

- “寻找重复逻辑并解释为什么应合并”
- “删除前先证明不可达”
- “跨模块修改必须跑契约测试”

少写穷举式死规则。原则和原因让 Agent 能在新场景里推理,也更容易被人审查。

### 4. 改进器:只提交候选 diff

改进 Skill 从 Wiki 读取高质量信号,提出一个小而可逆的修改。它的产物是 PR 或 patch,不是直接覆盖生产 Skill。

候选 diff 至少写清:

- 要解决的失败模式
- 引用的反馈与轨迹
- 为什么不是一次性例外
- 影响哪些任务
- 用什么测试证明改善
- 哪些旧行为可能回归

## 一次完整更新怎么走

### 第一步:在人本来工作的地方收反馈

代码审查就读 PR 评论,客服 Agent 就读工单纠正,文档 Agent 就读编辑记录。不要另建一份没人愿意填的“AI 反馈表”。

低摩擦不等于匿名。每条反馈仍要保留来源、上下文和最终处理结果。

### 第二步:过滤谁的反馈有资格进入 Wiki

不是所有评论权重相同。最小权限表可以是:

| 反馈来源 | 可进入原始轨迹 | 可进入 Wiki | 可触发 Skill 更新 |
|---|---:|---:|---:|
| CI / 确定性检查器 | 是 | 是 | 是 |
| 领域负责人详细评论 | 是 | 是 | 是 |
| 普通审阅者有证据的评论 | 是 | 审核后 | 审核后 |
| 点赞/反对、无理由评价 | 是 | 否 | 否 |
| 外部不可信输入 | 隔离保存 | 否 | 否 |

反馈质量通常比数量重要。少量领域专家给出的“为什么”比大量二元评价更有训练价值。

### 第三步:先更新理解,再更新指令

新反馈先进入 Wiki,和历史证据对照。只有在多个任务中重复出现、因果关系清楚、能被一般化时,才生成 Skill diff。

这一步能防止“刚失败一次,全局立刻加一条禁令”。

### 第四步:只改一个可以验证的点

一次 diff 解决一个失败模式。不要同时改触发条件、工作流、输出格式和工具权限,否则即使指标变好也不知道是哪处生效。

### 第五步:跑留出集,不能只重放训练案例

至少准备三组任务:

1. **修复集**:原来失败的案例,应当转绿。
2. **回归集**:原来通过的案例,不能变差。
3. **留出集**:改进器没见过的同类任务,验证规则是否真的可泛化。

有确定答案的领域,以测试、部署或检查器退出码为准。没有统一答案的领域,使用领域专家盲审,不要让改进器自己给自己打分。

### 第六步:人工批准,带版本发布

审阅者需要同时看到 Skill diff、来源证据和评测差异。批准后打版本号;上线指标变差时,能一键回退到上一版。

## 主观任务为什么更危险

@dotey 的写作 Skill 实验点出了关键边界:写作没有统一正确答案,反馈常常互相冲突。一个人说“更简洁”,另一个人说“信息不够”,Agent 可能在两个方向之间来回摆动。

这类任务需要:

- 明确谁是最终风格所有者
- 把偏好限定在具体输出类型
- 保存相反意见,不强行合并成普遍规则
- 用成对盲审而不是单一自动分数
- 提高发布门槛,降低自动更新频率

## 轨迹投毒是权限问题,不是提示词问题

轨迹投毒研究提醒了一个反直觉风险:**攻击者不需要直接编辑 Skill,只要反复贡献“看起来有用”的失败经验,就可能诱导改进器把目标行为写入长期规则。**

因此:

- 不可信轨迹永远不能直接晋升
- 同一来源的大量反馈不能冒充独立共识
- 更新依据必须保留 provenance
- 改进器不能修改自己的评测门槛
- 涉及权限、发送、支付、删除的规则默认禁止自动放宽
- 新 Skill 版本先在隔离环境和影子流量运行

论文报告了较高的攻击成功率,但这些数字来自特定实验设置,不能直接外推到任意生产系统。应该吸收的是安全边界,不是把论文百分比当作自身风险概率。

## 最小可落地目录

```
agent-system/
  skills/
    code-review/
      SKILL.md
      references/
  evidence/
    immutable-runs/
  wiki/
    review-lessons.md
  evolution/
    updater-skill/
    proposals/
  evals/
    fix-cases/
    regression-cases/
    holdout-cases/
  approvals/
```

目录不是重点,边界才是重点:

- `evidence/` 不可由 Agent 改写历史
- `wiki/` 记录理解和来源
- `skills/` 只存当前可执行版本
- `proposals/` 与生产版本隔离
- `evals/` 不归改进器所有
- `approvals/` 留下谁批准了什么

## 发布前检查清单

- [ ] 这次更新引用了哪些真实失败和人类反馈?
- [ ] 反馈者是否有权影响这个 Skill?
- [ ] 它解决的是重复模式,还是一次性例外?
- [ ] Wiki 是否记录了原因、反例和适用条件?
- [ ] diff 是否只改一个可归因的点?
- [ ] 修复集、回归集、留出集是否全部运行?
- [ ] 评测判据是否独立于改进器?
- [ ] 主观任务是否经过领域专家盲审?
- [ ] 权限是否被扩大?若是,是否单独审批?
- [ ] 是否有版本号、观察期和回滚路径?

## 适用边界

- **最适合反馈天然存在的流程。** PR、工单、编辑记录都能提供低摩擦信号;没有稳定人类反馈的场景,不要为了“自我进化”伪造反馈。
- **最适合重复任务。** 同类代码审查每天发生,经验才有复利;一年只做一次的任务没有足够样本。
- **不能替代正确性判据。** Skill 学会“怎么做”之后,代码仍要测试,部署仍要探活,数据仍要核验。
- **主观任务要更慢。** 写作、设计和战略判断容易负优化,应减少更新频率并提高人工门槛。
- **小团队也有维护成本。** Wiki、留出集、版本和审批都需要人维护;任务量很小时,手工改 Skill 可能更便宜。
- **这是持续治理,不是一次配置。** 反馈来源、评测集和权限边界都可能漂移,必须定期审计。

## 一句话

**让基础 Skill 执行,让人类在原工作流里纠正,让持久 Wiki 累积理解,让改进器只提候选 diff;通过独立评测和人工批准后再发布,并始终保留回滚。**
