# 先收敛工具栈,再扩展个人 AI 工作站

> **出处** — [@fankaishuoai](https://x.com/fankaishuoai/status/2101625967882199247) · 采集于 2026-09-21
> **原作者说法**:作者长期在一台 Mac 工作站上运行自己的 AI 基础设施,用虚拟网络远程接入、文件同步工具同步资料、远程桌面处理人工操作,并把 Agent 调度与普通自动化分开:需要 Bot/语义判断的任务交给 Agent 和其计划任务,不需要模型的任务写成 Python 脚本交给系统定时器。工具和 Agent 最终收敛到少数稳定组合,模型用真实工作流而不是演示题评测。作者明确说现有工具约 70% 能力尚未用到,不再持续追新。
>
> 下文的分层方法、验收表和收敛规则是本仓库的工程化整理,不是原作者逐字给出的通用配置。

## 先画五层,不要先列软件名

1. **接入层:**远程网络、设备认证与人工接管,只解决“怎么安全地回来”。
2. **同步层:**代码、知识库和工作文件的同步,写清单向/双向、冲突与备份策略。
3. **确定性自动化层:**复制、清理、定时抓取、格式转换等规则明确的任务,优先脚本和系统调度。
4. **Agent 层:**需要理解上下文、选择工具或处理异常的任务,才调用 Agent;对外发送与高风险写入保留确认。
5. **模型层:**本地或云端模型按任务分配,不让模型品牌反过来决定系统结构。

先定每层职责,再为每层挑一个主工具和一个故障替代。这样更换模型、远程工具或同步软件时,不会把整个系统推倒重来。

## 判定一个任务是否需要 Agent

按顺序问四个问题:

- 输入和规则是否固定?固定就先写脚本。
- 是否需要理解自然语言、图片或模糊上下文?需要才考虑模型。
- 失败能否由退出码、文件哈希或页面状态判断?能就先补 checker。
- 是否涉及发送、支付、删除、部署或账户权限?涉及就保留人工闸门。

这一步能避免“因为已经装了 Agent,所以所有任务都让 Agent 做”。确定性任务使用模型,通常只会增加成本、波动和排障难度。

## 每月做一次收敛审计

给每个组件只记五项:承担的任务、每周使用次数、失败次数、人工介入时间、是否有替代品。

- 连续一个月没有真实任务使用:停用。
- 与另一组件职责重叠:保留更稳定、证据更清楚的一项。
- 只能在演示题里更快:不进入主流程。
- 加入后没有减少总人工时间:回滚或降级为实验工具。

模型比较也使用自己的固定任务集,记录成功率、时延、费用和返工时间;不拿“鹈鹕骑自行车”式展示代替工作流验证。

## 最小验收清单

- 断网或模型不可用时,确定性任务仍能运行。
- 每个自动任务都有日志、最后成功时间和失败通知。
- 同步冲突不会静默覆盖文件,且有可恢复备份。
- Agent 的外部写入、发送与付费动作有明确批准点。
- 换模型不需要重写接入、同步和脚本层。

## 适用边界

这套方法适合长期运行、跨设备接入且任务类型较多的个人或小团队工作站。只有一两个短期任务时,搭五层基础设施的维护成本可能高于收益。

原作者列出的具体软件与本地模型是个人选择,不是推荐清单;不同操作系统、网络和合规要求需要换实现。远程访问、浏览器登录态、支付与云账户都扩大权限面,不能因为“只在个人机器上”就省略最小权限、备份、审计和人工确认。
