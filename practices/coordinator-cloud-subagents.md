# 让本地 agent 只当协调者，把活派给云端子代理

> **出处** — [@poteto](https://x.com/poteto/status/2084844251100438890) · 采集于 2026-08-07
> **原作者说法**：日常工作流是「一个本地协调者 agent（local coordinator agent）+ 一批云端子代理（cloud subagents）」——实现工作全部丢给云端，本地那个只负责统筹，并确保子代理遵守自己那套 playbook。他还提到用一个 `swarm` 技能一次拉起十几个各自带独立 VM 的廉价子代理，让它们在云上跑起应用做模糊测试（fuzz），在合并 PR 之前先把问题挖出来。
> 个人经验，未经官方确认。原推提到的斜杠命令与技能名是他所用工具/自制技能的写法，**不通用**，本文只取可迁移的结构。
> **补充出处** — [@mattshumer_ 的 Manager Loop](https://x.com/mattshumer_/status/2095723177389232540) · 采集于 2026-09-04。下方阶段推进与边界是原作者经验和本仓库整理，不是本仓库实测。

本文在原推之外，补充了同期公开讨论里的实战细节与**失败模式**，并对照了两家厂商公开的相反立场。凡属本仓库补充的部分均已标注。

---

## 一句话

**本地那个 agent 不写代码，它只做三件事：拆任务、发任务、验收。**

真正干活的进程跑在别处（云端沙箱 / 独立 VM / 独立会话），干完把**结论**交回来，而不是把**过程**倒进协调者的上下文里。

## 它替代的是什么

不是替代「一个 agent 从头干到尾」，而是替代**本地多开并行**那套：开五个 worktree、五个终端、五个容器，然后自己在中间当人肉调度器。

同期讨论里几条具体的痛点（均为个人经验）：

- **端口和目录冲突**：本地并行最琐碎也最耗神的开销是「哪个 localhost 端口对应哪个会话」，换成各自独立的云端沙箱就不存在了 —— [@poteto](https://x.com/poteto/status/2084844251100438890)
- **环境漂移**：沙箱的价值不是"远程的 SSH"，而是**可复现**。本地工作区通常已经和上游漂移很久了，而每个 agent 都拿到完全一致的干净环境，才谈得上跑几百个并行 —— [@colemurray](https://x.com/colemurray/status/2073116277829464338)
- **人肉盯梢**：把"我在旁边看着五个 agent"这件事本身也交出去 —— 有人做了个 conductor agent 负责把每个云端 agent 的改动一路护送到生产，agent 自己开不了 PR 时由 conductor 代开、再回头通知它去要 review，全部跑完给自己发一条 Discord 总结 —— [@kentcdodds](https://x.com/kentcdodds/status/2084800662857277934)

## 真正的收益是上下文隔离，不是并行

这是整套模式里最容易被讲反的一点。原推底下有人一句话点破：

> 「并行是障眼法，上下文隔离才是真正的收益 —— 子代理污染不了协调者的脑子。」 —— [@harleyfoote_](https://x.com/poteto/status/2084844251100438890)（原推回复）

**为什么这条比"更快"重要：** 协调者的上下文里如果混进了三个子任务的调试过程、报错、试错分支，它做调度判断的质量会肉眼可见地下降。子代理各自持有自己的上下文窗口、只回传一份摘要，协调者的记录才干净。

Anthropic 公开的研究系统数据可以作为参照（厂商自述）：他们的 lead agent + subagents 架构在内部研究评测上比单 agent 高 **90.2%**，但**多 agent 系统消耗的 token 约是普通聊天的 15 倍**（单 agent 约 4 倍）；他们也直说 token 用量本身能解释浏览类任务 80% 的性能差异。换句话说，**这套东西是拿钱换质量和时延的**，不是白捡的。

## 协调者该怎么发任务

Anthropic 那篇里给的子任务描述四要素最值得抄（官方口径）：每个子代理必须拿到 **目标 / 输出格式 / 工具与信息源的指引 / 明确的任务边界**。他们踩过的坑是：任务描述不够细时，子代理要么重复劳动，要么集体漏掉同一块。

本仓库补充的落地写法：

```
# 派给子代理的任务模板
目标：  <一句话，可判定完成与否>
产出：  <PR / 报告 / 补丁文件；要什么格式说死>
范围：  <只准动哪些目录/文件；明确列出不要碰的>
验收：  <跑哪条命令、期望什么输出；测试不过不许回报完成>
禁止：  <不要顺手重构、不要改依赖版本、不要格式化无关文件>
```

「禁止」那一栏是实战出来的：子代理在自己的上下文里看不到别人正在改什么，**顺手重构是并行场景下最贵的破坏**。

规模上，Anthropic 的经验值是 lead agent 并行拉 **3–5 个**子代理；社区讨论里 Claude Code 生态给的经验值也是 3–5 个并发为多数任务的甜点区。再多主要是协调开销和去重成本。

## 成本：让协调者和执行者用不同的模型

这条是多方独立得出的同一结论：

- **协调者不必是最贵的模型，甚至不该是。** 有人转述 Cognition 的 sidekick 评测结论：Fable 当协调者比 Opus **更便宜**，因为它更少微观管理、更愿意真的把活委派出去；同时建议**反复委派给同一个子代理会话**，成本和效果都更好 —— [@brandon_galang](https://x.com/brandon_galang/status/2076825404673769909)（转述评测，未核实）
- **强规划模型 + 廉价执行模型**：有人用高推理档做 Orchestrator、拉 3–5 个便宜档 Executor 并行干活，自述成本约降到 1/3 —— [@RealYDT](https://x.com/RealYDT/status/2075355302309113889)（个人经验）
- **注意子代理会继承主模型**：有人指出某些原生多代理实现**不能给不同子代理单独指定模型和推理强度**，一旦并行，子代理全部继承主模型 → token 成本迅速失控；他的绕法是不用原生的 spawn，而是调用"新建独立后台线程"的能力，把每个 worker 建成独立任务，从而能分别指定模型 —— [@zjp1997720](https://x.com/zjp1997720/status/2076605089523876191)（个人经验）

**照做前先查一件事：你的工具能不能给子代理单独指定模型。** 不能的话，"并行 5 个"约等于"账单乘 5"。

## 失败模式（这套模式最贵的部分）

同期讨论里被点名的、以及厂商公开承认的失败模式，按危险程度排：

| 失败模式 | 表现 | 应对 |
|---|---|---|
| **未经批准的自动扇出** | 你只提了一个任务，harness 自己把它扩成十几个并行子代理，而每个子代理都完整复制一份系统指令、项目规则、对话历史与既往结果 | 见下节。先确认你的工具会不会自动扇出，再决定要不要给递归生成设上限 —— [@Breeze1055Liu](https://x.com/Breeze1055Liu/status/2090407566883058064)（个人取证，未经官方确认） |
| **谎报完成** | 子代理返回"部分状态"却标记为成功，协调者信了继续往下走 | 验收靠**命令的退出码/产物**，不靠子代理的自述。<br>「比本地失败难查得多」 —— [@bygregorr](https://x.com/poteto/status/2084844251100438890)（原推回复） |
| **环境退化** | 不是崩溃，是**质量悄悄下滑**——沙箱缺了它执行或验证所需的环境 | Cursor 官方称这是最隐蔽的失败模式，他们的解法是让 agent 主动上报缺失的密钥/被拦的访问并自行修复 |
| **重复发现** | 十个子代理探同一个应用，会发现同一个底层 bug 并用十种说法描述 | 协调者需要一个**稳定的去重键**（如「文件 + 症状」）在入队前合并 —— [@AIAppsAPI](https://x.com/poteto/status/2084844251100438890)（原推回复） |
| **互相等待** | staging 正常、生产 30% 请求超时，日志显示 A 等 B、B 等 A | 拓扑上就别让子代理互相依赖：**同一批次内的任务必须彼此独立**，有依赖就分批 —— 由 [@avrldotdev](https://x.com/avrldotdev/status/2084600500113092660) 的面试题引出 |
| **决策冲突** | 各子代理基于各自的隐含假设产出，拼起来对不上 | 见下节的反方立场；缓解办法是把关键决策**在派发前定死**写进任务描述，而不是让子代理各自现场决定 |
| **嵌套限制** | 从云端子代理里再拉起云端子代理不生效 | 有用户反馈这条限制真实存在（工具相关）—— [@fatih](https://x.com/poteto/status/2084844251100438890)（原推回复）。设计时假设**只有一层** |
| **本地反而被吃满** | token 从云端流，本地 CPU 仍被并行 harness 占满 | 并行度别按"反正在云上"来定 —— [@usmanpirzada](https://x.com/usmanpirzada/status/2084641663679332758)（个人经验） |

## 上下文隔离的反面：同一份上下文被复制了 N 遍

上面说「真正的收益是上下文隔离」，但隔离有个前提——**子代理拿到的是被裁剪过的任务描述，而不是主会话的完整副本**。这个前提一旦不成立，隔离就变成了复制，而复制是按 token 计费的。

2026-08-20 有用户拿本地 `token_count` 账本给出了一组具体数字（**个人取证，未经官方确认，官方亦未回应**）：他只让工具处理一个 issue，系统却**未经批准**自主扩成 **11 个**并行子代理做审计/实现/复核，每个子代理都完整复制了系统指令、项目规则、对话历史与既往结果。那次重置之后他记录到约 **6.08 亿 token** 消耗，其中约 **5.14 亿（约 85%）来自子代理** —— [@Breeze1055Liu](https://x.com/Breeze1055Liu/status/2090407566883058064)

**为什么这条值得单列，而不是并进上面那条「子代理继承主模型」：** 那条讲的是*单价*（子代理用了更贵的模型），这条讲的是*基数*（同一份上下文被计费了 11 次）。两者会相乘。而且这一次的扇出是工具自己决定的，用户从头到尾没批准过——**上面整篇讲的都是「你怎么派任务」，这条讲的是「它可能不等你派」。**

本仓库补充的排查动作（顺序即优先级）：

1. **先确认你的 harness 会不会自动扇出。** 有没有「自动并行子代理 / 自动拆解任务」这类默认开启的行为，是不是需要审批。这决定了后面几步要不要做。
2. **按子代理分别看 token，而不是只看总量。** 总量只告诉你「花超了」，分项才告诉你「花在复制上」。上面「给每个子代理留独立日志」那条，顺带也把这件事解决了。
3. **看子代理拿到的输入里有没有整段对话历史。** 派发模板里的目标/产出/范围/验收/禁止五要素是**替代**完整历史用的，不是**追加**在它后面的。
4. **给递归生成设上限。** 上文说「设计时假设只有一层」是从功能角度讲的（嵌套可能不生效）；从成本角度讲，你还需要它**确实**只有一层。

> **判断这条值不值得你花时间的最快方法：** 如果你觉得额度在刚重置之后就掉得离奇快，那很可能不是配额被调小了，而是消耗侧被放大了——扇出通常发生在任务开头。反之，如果你的用量曲线平滑，这条可以先跳过。

**边界：** 上述数字出自单个用户的本地记录，**未经第三方或官方核实**，不同工具、不同版本的扇出行为差别很大，别把 85% 当成普遍值；把它当成一个**该去自查的方向**，不是一个该去引用的结论。这条也不构成「别用子代理」——本文整篇的立场没变，变的是「派出去之前先知道会被复制几份」。

### 2026-08-21 增补：官方给了第一诊断入口

上面那一节整节都建立在**一个用户的本地账本**上，所以它当时只能算"该去自查的方向"。这一天官方那侧补上了入口——Claude Code 负责人在两位用户追问"额度为什么烧这么快"时给了同一个答案：

> 跑 `/usage` 看详细分解。绝大多数情况是三个原因之一：**极端并行（extreme parallelism）、跑飞的循环（runaway loop）、或某个效率极差的 skill/plugin。**

这条之所以值得记进来，不在于它给了新技巧，而在于它**改变了这类问题的性质**：

- **"额度不够用"从一句抱怨变成了一个有诊断树的工程问题。** 三个候选原因是互斥且可分别验证的——并行看的是同时有几个子代理在跑，循环看的是同一个工具调用是不是在重复，低效 skill/plugin 看的是单次调用返回了多少不需要的内容。
- **官方把"极端并行"列在第一位**，与上一节那份个人取证指向同一个方向。两个独立来源（一个官方、一个用户账本）都落在扇出上，这比任何一方单独说都更值得当真。
- **它给了排查的起点，没给结论。** `/usage` 只告诉你钱花在哪，不告诉你该不该花——判断仍然是你的：上一节那四步排查动作接在这一步后面用。

**顺序建议：** 先 `/usage` 看分项（1 分钟，官方口径），再按上一节四步查扇出（半小时，需要看日志）。**别跳过第一步直接改配置**——如果你的消耗其实是一个跑飞的循环，限制子代理数量一点用都没有。

**边界：** 这是员工在推文回复里给的口径，不是文档，也没有说明 `/usage` 在各订阅档位下的分项粒度；`/usage` 是 Claude Code 的命令，其他工具需要找各自的等价物（有没有按子代理分项的用量视图，本身就是选型时该问的一个问题）。

## 反方立场：Cognition 说别建多代理

引用这套模式之前，应该知道有一份影响力很大的相反主张。Cognition 的 *Don't Build Multi-Agents* 给的两条原则是：

1. **共享上下文，而且要共享完整的 agent 轨迹，不只是单条消息**
2. **行动携带隐含决策，冲突的决策带来糟糕的结果**

他们的例子：让子代理并行做一个 Flappy Bird，一个子代理把背景做成了马里奥风格，另一个做的鸟和背景对不上——因为各自的隐含假设从没交换过。结论是**默认用单线程线性 agent**；上下文实在超长就加一层压缩（专门的模型把历史蒸成关键决策与事件），而不是拆成多个 agent。

作者后来的公开表态是：一年前他会劝人别建多代理、专注上下文工程基础，如今**有一些配置确实跑得通了**，但收窄的设计更好——**让写操作保持单线程，额外的 agent 贡献"判断"而不是"动作"**。

> **怎么调和这两派：** 这不是谁对谁错，是**任务形态**的差别。Anthropic 那套并行有效的场景是**广度优先的检索**（多个独立方向同时找信息，子代理是过滤器，回传的是结论）；Cognition 反对的场景是**同一件产物被多个 agent 分头写**（子代理各写一块，隐含假设冲突）。Anthropic 自己也明说：**大多数编码任务并行度低、依赖多、需要共享上下文，并不适合多代理。**
>
> 落到本文这套模式上的推论：**派出去的应该是"能独立验收的整块任务"，不是"同一件东西的几个零件"。** 一个 PR 一个子代理，可以；一个 PR 拆给三个子代理写三段，别做。

## 增补：Manager Loop 用阶段进度对抗长程停滞

> **原作者说法**：Astra 在极长任务里会逐渐陷进细节，整体目标的推进速度趋近停滞。作者先由人工拿着清单逐阶段推动，后来把这项工作交给单独的 manager agent：manager 拆阶段、派发并观察进度，implementer 专门执行。他称这比自己的其他尝试表现更好，但没有公开统一对照数据。

可迁移的做法不是某个斜杠命令，而是**把“推进任务”和“完成当前阶段”分给两个角色**：

1. **先建立完整清单，再分成有先后关系的阶段。** 每个阶段都写产物和外部验收条件，不能只有“极好地完成”一类主观要求。
2. **经理只派发和验收，实现者只改当前阶段。** 当前阶段未通过 checker 时不进入下一阶段；通过后，经理明确关闭这一阶段，再发下一项。
3. **共享进度看板只记录可验证变化。** 勾选项必须对应真实产物、测试或审阅，不允许 agent 自己写一句“完成”就计数。
4. **用停滞信号触发重新规划。** 一段时间没有新增有效勾选时，先检查是否卡在无价值细节、错误依赖或不可达目标；该拆分就拆分，该升级给人就升级，不能只是命令它“继续”。
5. **完成后做一次全局回归。** 分阶段绿不代表组合后仍然正确；最终由独立检查者运行整体验收。

原作者提到用“extremely well”而非“perfectly”可减少模型钻牛角尖，也提到并行 96 个子代理。前者只是个人措辞经验，后者高度依赖算力、配额和任务独立性，**都不是这套结构的必需条件**。

### 适用边界

- 适合目标相对明确、可以拆出阶段产物、且每阶段有外部检查的长任务。
- 不适合需求仍在探索、阶段之间频繁互相改写、或唯一验收标准只是人的整体品味；此时经理会把错误路线自动推进得更远。
- 清单项大小不一，勾选数不能当作真实完成百分比。看板应同时显示关键路径和阻塞项。
- manager 和 implementer 互相发消息不等于证据。测试退出码、构建结果、真实产物与人工批准仍是闸门。
- 子代理数量应由任务独立性、审查带宽和预算决定；未经批准的高并发或递归扇出可能把额度迅速放大。

## 今天就能改的五件事

1. **把协调者降级。** 把最贵的模型从"执行"挪到"验收"，协调者换成更便宜、更愿意委派的档位。先跑一周对比账单。
2. **给子任务补上"禁止"栏。** 现有的派发模板里大概率只有目标没有边界，加上"不要动哪些文件、不要顺手重构"。
3. **把验收从自述改成证据。** 子代理回报完成时必须附上命令输出或产物路径；协调者只认证据不认结论。
4. **查一次自动扇出。** 打开工具设置，确认它会不会不等你批准就把一个任务拆成十几个并行子代理；会的话，看看能不能要求审批或设上限。这一步比下面三步都快，而且可能是最省钱的一步。
5. **给每个子代理留独立日志。** 有人提到必须逐子代理单独留日志，才看得出是哪一步走偏的（原推回复，韩语）。合并成一份总日志等于放弃排障能力。

## 边界

- **本文描述的是"形状"，不是某个产品的操作步骤。** 原推提到的斜杠命令、技能名、云端 API 都与具体工具绑定；换工具时保留的是「协调者不干活 / 派整块任务 / 验收看证据」这三条。
- **不适用的场景**：需要频繁人工介入的探索性工作（原作者本人也说这类他仍留在本地）；重度依赖内部 API 与本地数据库、沙箱里根本跑不起来的应用（原推回复里就有人卡在这），除非你先把 mock 数据这层建好。
- **成本不是小数**：多代理的 token 量级是聊天的十几倍（厂商自述）。任务不值这个价就别派。
- 引用的社区经验绝大多数是**个人实践、未经第三方验证**；厂商数字为其自述，未独立核实。
