# 社区模型变体先审工件,别只信模型页

> **出处** — [@xiangxiang103](https://x.com/xiangxiang103/status/2102704760122146992) · 采集于 2026-09-24
> **原作者说法**:作者检查一个社区模型仓库时,发现模型页宣称的“保留官方原始权重”并不准确。同仓库的 base 与 main 分支文件 tensor 结构相同,但抽查多个位置后约 15% 字节不同;维护者没有说明具体修改。作者还指出,完整生成链不只有主模型,还包含提示改写器、文本编码器与 VAE,其中任一环节都可能改变拒绝、输出或性能。作者随后更正了自己的早期说法,并提醒仍受原研究许可证约束。
>
> 下文的固定审计流程、风险分级与验收清单是本仓库的工程化整理。本文讨论供应链验证,不建议移除模型安全措施或绕过平台规则。

## 第一步:冻结你实际拿到的工件

记录仓库 URL、分支、commit、release/tag、下载时间和每个文件的 SHA-256。不要只写“某某 Q4 版”,因为同名文件可以被替换,不同分支也可能内容不同。

把许可证、模型卡、README 和启动参数一并保存。它们是同一次审计的输入,后续上游更新不应静默改变结论。

## 第二步:结构相同不等于权重相同

至少比较四层:

1. 文件大小与哈希;
2. tensor 名称、shape、dtype 和数量;
3. 对应 tensor 的采样值或块级哈希;
4. 配置、tokenizer、system prompt 与特殊 token。

“能加载”“tensor 结构一样”“文件名带 base”都不能证明来自官方原始权重。发现差异时先记为**未知修改**,不要替维护者猜原因。

## 第三步:画完整加载链

模型行为可能由多个工件共同决定:

`用户输入 → 提示改写/路由 → tokenizer/文本编码器 → 主模型 → 解码器/VAE → 后处理`

逐项记录实际加载的文件、节点和参数。只替换主模型却忽略改写器或编码器,会把上游行为误归因给主模型;同理,安全策略也可能分布在多个环节。

## 第四步:做成对照矩阵

固定种子、输入、采样参数与硬件,分别运行官方版、社区变体和你认为的 base 分支。记录:

- 输出是否成功、拒绝与错误类型;
- 质量与任务正确性;
- 峰值显存、时延和稳定性;
- 是否出现额外网络请求、文件读写或自定义代码执行。

行为差异只能证明“这组工件在这组条件下不同”,不能单独定位是哪一层修改导致。

## 放行清单

- 工件来源、哈希、许可证和 commit 可追溯;
- 自定义代码经过只读审查,默认禁止远程代码执行;
- 完整加载链中的每个文件都被列出;
- 差异被标为已解释或未知,没有用营销标签代替证据;
- 在隔离环境完成恶意文件、网络和资源占用检查;
- 生产使用前保留官方版回退路径。

## 适用边界

这套方法适合社区量化、微调、合并模型、格式转换和第三方启动包。它不能证明训练数据、原始训练者或法律权属,也不能保证没有触发式后门;高风险场景仍需可信构建、签名、沙箱与专业安全审计。

字节不同不等于恶意,量化和格式转换本来就会改变权重。关键是修改是否可解释、可复现、与许可证和模型页一致。对安全措施的移除尤其要谨慎:技术上可运行不代表合规、可靠或适合对外服务。
