# 用 token 差分给匿名模型做词表指纹

> **出处** — [@ScarletKc_](https://x.com/ScarletKc_/status/2090771749357150451) · 采集于 2026-08-22
>
> **原作者说法**：当匿名模型的 API 仍返回 `prompt_tokens` 时，可以用“同一基准请求”与“基准请求加特征后缀”的 token 数差值，消掉固定系统提示词的影响，再与多个已知模型端点交叉比较。原作者用四组文本得到与某一模型家族完全一致的计数，因此把它作为词表家族的旁证。

下面的实验结构、置信度分级、复测要求和适用边界是本仓库补充的工程化落地；具体模型归属仍以厂商正式披露为准。

## 它解决什么问题

匿名模型的自我陈述很容易被系统提示词控制，诱导它“说出身份”通常只能证明提示词约束，不足以证明模型来源。

词表切分则位于更底层：相同文本在不同 tokenizer 下可能产生不同 token 数。只要服务端返回输入 token 计数，就能把它变成一个可重复测量的侧信号。

## 实验步骤

1. **固定请求外壳。** 模型、消息角色、采样参数、工具定义和其它请求字段全部不变，只改变用户文本。
2. **发送基准请求。** 用短文本 `X` 记录 `prompt_tokens_base`。
3. **发送探针请求。** 改成 `X + suffix`，记录 `prompt_tokens_probe`。
4. **计算差值。** `delta = prompt_tokens_probe - prompt_tokens_base`。如果两次请求的固定前缀相同，隐藏系统提示词和固定模板通常会在相减时抵消。
5. **准备多组特征后缀。** 至少覆盖生僻字、超长英文单词、中英数字混排、日韩混合等切分差异较大的文本；不要只用一组普通英文句子。
6. **建立对照矩阵。** 对每个候选官方端点运行完全相同的请求，记录每组后缀的 `delta`，再与匿名模型逐列比较。
7. **重复测量。** 在不同时间复跑，确认计数稳定，并记录模型名称、API 版本、日期和请求参数。

可以把结果整理成这样的最小表格：

| 端点 | 探针 A | 探针 B | 探针 C | 探针 D |
|---|---:|---:|---:|---:|
| 匿名模型 | Δ | Δ | Δ | Δ |
| 候选模型 1 | Δ | Δ | Δ | Δ |
| 候选模型 2 | Δ | Δ | Δ | Δ |

## 怎么解释结果

- **单个探针相同：弱证据。** 很多 tokenizer 会对普通文本给出相同计数。
- **多组高区分度探针全部相同：中等证据。** 可以支持“共享 tokenizer 或属于同一词表家族”。
- **再加独立行为证据：较强旁证。** 例如稳定的格式、知识边界或已公开架构特征，但这些证据也可能被后训练和系统提示词改变。
- **只有厂商披露或可验证的模型工件才能确认具体身份。** token 差分不能单独证明具体版本、参数规模、训练主体或所有权。

## 工程化落地

- 把探针文本、请求 JSON、原始响应和计算脚本一起版本化，避免只保存结论。
- 每个候选端点使用同一 API 路径与消息格式；网关若重新序列化消息，应单独列为实验变量。
- 先跑空白对照和重复性检查，再增加候选模型，防止把计费器抖动误判成词表差异。
- 给结论标置信度，并保留“共享 tokenizer”这个更保守的解释。
- 模型或网关更新后重新跑基线；旧指纹不能永久沿用。

## 适用边界

- API 必须返回稳定的输入 token 计数；如果只返回总量、四舍五入或延迟聚合数据，这个方法不可用。
- 两次请求的固定部分必须真正相同。工具 schema、图片、缓存策略、自动插入的元数据或服务端路由变化都可能污染差值。
- 同一家族甚至不同模型可能复用同一个 tokenizer，因此完全匹配通常只能定位到词表家族。
- 服务端可以更换 tokenizer、隐藏计数或对计费 token 做额外处理，指纹会随实现变化。
- 测试应遵守服务条款与速率限制，不用越权、绕过访问控制或诱导模型泄露受保护信息。

## 最小结论

**不要问匿名模型“你是谁”，要测量它如何切分同一段文本。** token 差分能把身份猜测从话术对抗提升为可重复实验，但它是归因旁证，不是身份证明。
