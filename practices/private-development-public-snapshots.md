# 私有开发,公开快照:把 Agent 的完整工作区与开源发布面分开

> **出处** — [@rough__sea](https://x.com/rough__sea/status/2092091242377265562) · 采集于 2026-08-25

> **原作者说法**:Ryan Dahl 公开了他开发 celld 的实际方式。公开仓库只是一个更大私有仓库的导出;私有侧包含 llm-wiki、设计文档、大型测试套件、TLA+ 规范、网站代码、多云实例与实验脚本,以及可能商业化的控制平面。他把审阅 `wiki/design/` 视为主要开发活动,常用 2–10 台云主机跑实验并用图表讲清结果;个人工作台通过 SSH / tmux 连接 Mac mini,同时运行约 2–4 个 Codex 与 Claude 会话。作者给出的理由包括避免公开每个中间提交、降低未成熟设计与潜在 IP 的暴露,以及认为大多数报告清楚的问题可由编码 Agent 快速解决。这是作者个人经验,没有独立验证。

下面「工程化落地」与「适用边界」是本仓库补充,不是原作者的说法。

## 它要解决的问题

编码 Agent 会把探索速度推得很快,但探索过程并不都适合实时公开:大量失败实验、未定稿设计、内部测试数据、部署脚本和潜在商业组件混在一起时,公共仓库既容易泄露不该发布的内容,也容易让外部读者把中间态误认成承诺。

相反,如果为了“保持仓库干净”而不保留设计与实验上下文,Agent 每次又要重新猜测系统为什么长成这样。结果是公开面整洁了,内部推理链却丢了。

这条实践给出的结构是:**私有仓库承担完整开发记忆,公开仓库承担经过验证的发布快照。** 两者不是简单镜像,中间要有一道明确的发布闸门。

## 原作者的做法

可以拆成四个相互配合的动作:

1. **把设计记忆留在私有开发仓库。** llm-wiki 与 `wiki/design/` 不只是背景资料,而是日常审阅和推进设计的主要界面。
2. **让验证资产与实现放在同一开发面。** 测试套件、TLA+ 规范、网站和云端实验脚本跟随代码变化,避免 Agent 只看到实现、看不到约束。
3. **用临时环境做有边界的实验。** 一次拉起 2–10 台云主机,运行一个实验,再用图表表达结论。实验环境不是常驻生产系统。
4. **控制并行度。** 作者实际只开约 2–4 个 Codex / Claude 会话,没有用代理数量充当产出指标。

公开仓库在这个结构里是发布物,不是开发过程的逐提交直播。

## 工程化落地(本仓库补充)

### 1. 先定义两个仓库各自拥有什么

最少写一张边界表:

| 资产 | 私有开发仓库 | 公开仓库 |
|---|---|---|
| 未定稿设计、失败实验 | 保留 | 不发布 |
| 可运行源码 | 主版本 | 经发布闸门导出 |
| 测试与规范 | 完整保留 | 发布足以验证公开承诺的子集 |
| 凭据、内部地址、客户数据 | 仅用安全引用,不入库 | 永不发布 |
| 商业组件 | 明确隔离 | 只发布许可证允许的接口或实现 |

“私有”不等于可以存明文密钥。凭据仍应进入密钥管理系统,仓库只保留变量名和获取方式。

### 2. 把快照导出做成可重复命令

不要靠手工复制文件。维护一份允许清单,只导出明确批准的目录;每次生成快照后运行测试、许可证检查、密钥扫描和差异审查。闸门全部通过后,才允许公共仓库产生一个可追溯提交。

建议快照记录至少包含:

- 私有源提交标识;
- 导出规则版本;
- 公开测试的退出码;
- 被有意排除的组件类别;
- 人工审阅者与发布日期。

源提交标识只应使用不会暴露私有远端地址或内部项目名的值。

### 3. 让设计文档与验证结果联动

每个进入 `wiki/design/` 的关键决策至少要链接一个验证物:测试、形式化性质、实验脚本或结果图。Agent 可以帮助补文档和跑实验,但不能用“文档写完了”代替 checker 通过。

定期扫描“实现已改、设计未更新”和“设计已批准、没有验证物”两类漂移。否则 llm-wiki 很快会从开发记忆变成误导 Agent 的陈旧上下文。

### 4. 给外部贡献保留清晰入口

公开快照不应等于关闭社区。公开仓库至少要说明如何报告问题、哪些目录接受补丁、何时同步下一快照,以及外部补丁如何回流私有开发仓库。没有这层说明,贡献者会反复撞上“公开代码不是当前开发头”的隐形墙。

## 适用边界

- **适合开发过程含未成熟设计、实验基础设施或潜在商业 IP 的项目。** 如果项目的核心价值就是开放协作与每个决策都公开,私有主仓库会直接伤害目标。
- **公开仓库必须保留足够验证资产。** 只扔源码、不发测试和构建方式,会让“开放”变成不可审计的代码快照。
- **私有仓库会形成单点真相风险。** 需要备份、访问控制、离职交接与恢复演练;不能让整个项目只存在于一个人的机器和会话里。
- **双仓库会产生同步成本。** 安全修复、外部补丁和许可证变更都要有回流路径,否则公开版本会长期落后且无人知道差距。
- **并行 Agent 数量不是目标。** 2–4 个会话是作者的个人工作量级,不是推荐上限。应该按审查能力和任务独立性决定,而不是照抄数字。
- **原作者没有给出对照实验。** “working well for me”只能证明这套流程适合他的当前项目,不能证明它优于公开主干开发。

## 一句话

**把完整设计、测试与实验留在受控开发面,把公共仓库当成经过测试和审查的发布快照;中间那道可重复、可追溯的导出闸门,才是这套结构的核心。**
