# 把日常维护拆成每天自动跑的例程,而不是攒一次大重构

> **原作者说法**:他在团队里建了一个专用频道,让智能体每天跨 iOS / 安卓 / 桌面 / 网页 / 命令行 / SDK 各端跑一组固定例程——崩溃模糊测试、重复抽象合并、死代码清理、抽象纠察等。几周下来这些例程开了 **388 个 PR,经代码审查 + 人工复核后合并了 180 个**(作者自述数字,未核实)。他强调:智能体通常一次就能把 PR 提对,提不对时**不是自己上手改,而是让它去调自己的例程提示词,第二天重跑**,有时要连调几天才稳。他把这个实验描述为「early signs of life」,即还在早期验证阶段。

下面「工程化落地」与「适用边界」两节是本仓库补充的落地建议,不是原作者的说法。

## 它要解决的问题

存量代码库里有一类活,人人知道该做、永远排不进优先级:死代码没人敢删、同一个概念有三套略微分叉的实现、崩溃只在特定路径复现、抽象漏得到处都是。它们单个都不值得开一张卡,攒到一起就变成「这块没人敢动」。

传统解法是攒一次大重构,风险集中在一次合并里。而把同样的工作交给智能体时,最容易犯的错是**照搬这个思路**——给它一个「重构整个模块」的大任务,然后收到一个几千行、没人能审的 PR。

这条实践给的是相反的形状:**同样的活,拆成粒度极小、每天自动跑一遍的例程,产出永远是小 PR,永远走人工审查。**

## 原作者的做法

四类例程是可直接照搬的模板:

| 例程 | 它每天干什么 |
|---|---|
| 崩溃模糊测试 | 在模拟器里打开应用乱点,找出能让它崩的路径,定位根因并修复 |
| 重复抽象合并 | 扫描代码库里相似却略有分叉的抽象,提 PR 把它们统一 |
| 死代码清理 | 删掉静态不可达的代码;**对「疑似死」的代码先加日志观察,确认没被调用,第二天再删** |
| 抽象纠察 | 修补泄漏的抽象 |

三个结构性选择比例程清单本身更重要:

1. **产出统一收敛到 PR**,再走代码审查 + 人工复核。智能体没有直接写主干的权限。
2. **失败时改的是例程,不是这次的输出**。这是它和「让智能体干活」最大的区别——每一次失败被当成例程提示词的 bug,修完明天生效,而不是这次手工兜底、明天再犯。
3. **跨端同一套机制**。例程是配置,不是给某个平台写死的脚本。

## 工程化落地(本仓库补充)

**先只开一条例程,而且从可逆的那条开始。** 死代码清理和重复抽象合并的爆炸半径完全不同:前者删错了 CI 会红、回滚即可;后者动的是别人正在改的文件,冲突和语义漂移都难查。建议顺序是:死代码清理 → 崩溃模糊测试 → 重复抽象合并 → 抽象纠察,越往后越需要人的判断。

**给每条例程写死「不许碰」的范围。** 生成的代码、迁移脚本、第三方 vendored 目录、正在进行的大分支涉及的文件,一律排除。这个清单写进例程提示词里,比事后在审查里拦便宜得多。

**「先加日志再删」这个手法值得单独拎出来推广。** 它把一个静态分析答不了的问题(这段真的没人调吗)换成了一个观测问题,而且代价只是一天延迟。同类问题都可以这么改:先加观测、跑一天、再动手。

**审查预算才是真正的瓶颈。** 每天 N 条例程 × 每条几个 PR,很快会超过团队的审查带宽——而没人审的 PR 堆积起来,比不开这些例程更糟。实践上限建议按「团队每天愿意花在这类 PR 上的审查时间」倒推例程条数,而不是按「智能体能跑多少」。原作者的合并率约 46%(180/388),意味着**过半的 PR 是要被关掉的**,这部分审查成本必须算进预算。

**给每条例程定一个留存判据。** 跑满两周后看它的合并率:持续低于某个线(比如 30%)说明这条例程的提示词还没调对,要么继续调,要么关掉——不要让一条常年被拒的例程一直消耗审查带宽。

**把调例程这件事本身固化下来。** 每次 PR 被拒时,把拒绝理由回灌给例程提示词。理想状态是维护一份「这条例程的已知禁忌」清单,随时间增长;否则同样的错误会以不同面貌反复出现。

## CI 值班 Agent：先写 SITREP，再沉淀 lessons

*(本节来自第二条官方团队实践；分层、护栏与验收建议为本仓库补充)*

Anthropic 工程负责人分享了团队正在使用的 CI 值班一线响应 Agent：它读取告警、指标与日志，先写一份 SITREP（态势报告），并在处理过程中维护 `lessons.md`。团队同时公开了模板和 skills。原推证明的是这套形态已在其 CI on-call 场景使用，不等于任何仓库接上模板都能安全自动修复。

将它落成一条可控流程：

1. **只读接入诊断面。** 第一阶段只给告警、指标和日志读取权，不给生产写权限、扩容权或发布权。
2. **先产出 SITREP。** 固定包含影响范围、开始时间、证据、已排除项、当前假设、下一步和需要人工决策的动作。
3. **明确停止边界。** 证据不足、告警相互冲突、需要修改生产或超过时间预算时，立即升级给值班人员。
4. **把建议与执行分开。** Agent 可以给命令、补丁或 runbook 建议，但真正执行通过独立审批门；恢复后还要由监控回落和用户路径共同确认。
5. **经验进入候选区。** `lessons.md` 先记录事件、证据和适用条件，经过复盘和人工审核后才晋升为正式 rule、skill 或 runbook。

这条实践把“每天维护”扩展到了“事件驱动维护”：日常例程按时间触发，CI 一线响应按告警触发；两者都必须把产出收敛到可审查对象，并把失败转化成下一轮更好的流程。

### 2026-09-14 增补：告警后按“指标—部署—开关”收窄原因

同一位 Anthropic 工程负责人补充了团队正在使用的另一条 on-call 链路：Slack 告警一出现，Claude 立即拉取指标、比对近期部署差异并检查功能开关，随后给出最可能原因和修复建议；**人类批准后才合并**。这条官方团队实践把上面的“读取告警、指标与日志”进一步收窄成可照做的诊断顺序。

建议把每次响应固定成五步：

1. **锁定告警快照。** 记录服务、症状、开始时间和告警链接，避免后续指标变化后无法复盘。
2. **先看指标是否真的偏离基线。** 同时查看影响范围、错误率、延迟和关键业务路径；没有偏离就先排查告警规则。
3. **把异常时间与部署差异对齐。** 只把时间上相关的 deploy diff 列为候选原因，不直接写成根因。
4. **检查功能开关和运行配置。** 区分代码变化、flag 切换与配置漂移，避免修错层。
5. **提交证据包和修复建议，等待批准。** 包含当前假设、支持证据、反证、补丁或回滚建议以及验证方法；批准与合并仍由人完成。

这条补充的价值不在于“Agent 反应更快”，而在于把 on-call 的前几分钟固定成一条可审计漏斗：**先确认症状，再对时间线，最后才提出动作。**

## 适用边界

- **一线响应不等于自主处置。** 数据库回滚、生产发布、删资源、改权限和对外通知等动作必须保持显式审批，不能因为 SITREP 看起来完整就自动执行。
- **SITREP 只能证明 Agent 看到了什么，不能证明故障已经恢复。** 关闭事件前仍需监控回落、真实用户路径和时间窗口内稳定性证据。
- **`lessons.md` 可能把偶发相关性固化成错误因果。** 每条经验必须带事件链接、证据、适用范围和反例；未经复盘不能自动变成所有项目的强制规则。
- **需要一个能兜住的审查回路。** 没有代码审查文化、或者 CI 覆盖不足的代码库,这套机制会把风险直接推到主干上。**审查是这条实践的前提,不是可选项。**
- **依赖测试与可回滚性。** 删死代码、合并抽象都靠 CI 兜底;测试覆盖薄的地方,这些例程的收益和风险会同时放大。
- **早期实验,不是成熟方案。** 原作者自己的定性是「早期迹象」。388/180 是一个团队、几周、特定代码库的数字,不能当成预期收益。
- **不适合语义密集的改动。** 业务逻辑重构、API 语义变更、性能优化这类需要领域判断的活,不适合做成无人值守的每日例程——例程适合的是**判据明确、正确性可被 CI 验证**的机械改动。
- **多人协作的活跃仓库要注意冲突。** 每天自动提的 PR 会和人的分支抢同一批文件,仓库越活跃,合并冲突的处理成本越高。可以先把例程限制在改动频率低的目录里。

## 一句话

**把「该做但永远排不上」的维护工作,拆成粒度小到可以每天自动跑一遍的例程,产出收敛为小 PR 走人工审查;做错时去调例程,不去调这一次的输出。**
