> **出处(补充)** — [@AYi_AInotes](https://x.com/AYi_AInotes/status/2088837685964075352) · 采集于 2026-08-16
> **原作者说法**:DeepSeek 开源 Harness 时,大家都在看架构和插件,却忽略了仓库里 `.agents/skills/` 目录——那里面放着 11 个**真实的工程 Skill**:代码评审、推送前检查、找过度设计、Stacked PR 合并、文档同步、双语翻译、思维链泄漏清理,甚至自动录制 GUI 验收 GIF。等于一家一线团队把自己每天在用的工程规范、评审方法和质量门禁开源了一部分,可以直接塞进自己的 agent 跑。
> 原作者的推荐是判断,不是实测报告;下面的清单核实、移植步骤与边界为本仓库补充。

## 这条实践到底在说什么

不是「又一个开源项目值得看」,而是一个**获取渠道的转变**:

写 agent 规范最难的部分从来不是写字,是**知道哪些检查值得做、以什么顺序做、做到什么程度算过**。这部分知识过去只存在于成熟团队的代码评审习惯里,外人拿不到。现在它开始以 skill 文件的形式随仓库一起发布——**这类文件是可以直接读、直接改、直接用的**,而且比任何「最佳实践清单」都可信,因为它们是被真实 CI 和真实评审磨出来的。

## 先看哪几个

*(本节为本仓库补充)*

不要一次全搬。按「与你现在的痛点是否对得上」挑:

- **`dsh-pre-push-checks`** — 收益最直接。绝大多数人让 agent 提交前的检查是靠嘴说的(「记得跑测试」),而这类文件把它固化成了一份清单。
- **`dsh-code-review`** — 想让 agent 评审自己产出的代码时,先读别人怎么定义「什么值得指出来」,比自己拍脑袋列维度快。
- **`dsh-find-simplifications`** — 少见但有价值:大部分人只让 agent 加东西,很少有人给它一份「怎么找该删的东西」的指引。
- **`dsh-trim-cot-leakage`** — 只在你的产物会外发(文档、回复、提交信息)时才需要,但那时它是刚需。
- **`record-browser-gif`** — 与[把审阅搬到产物上](visual-review-loop.md)是同一个方向:让验收物本身可看,而不是让人去读描述。

`dsh-doc-*` 和 `dsh-prose-standard` 高度绑定他们自己的文档站与文风,参考价值低于前面几个。

## 移植时必须改的四处

*(本节为本仓库补充)*

直接复制粘贴基本会失效。真正要做的是**读懂再改写**:

1. **工具与命令名**。里面写死的包管理器、构建命令、脚本路径都是他们仓库的,换成你的。
2. **仓库形态假设**。Stacked PR、monorepo、文档站同步这些流程,建立在特定的协作方式上;你如果是单仓库、单分支、两个人,照搬只会增加仪式感。
3. **触发描述行**。这批 skill 是为 dsh 自己的 agent 写的,描述行的措辞按它的加载机制来。挪到别的 harness 上,**描述行要按你的工具重写**——这一行决定它会不会被触发,见[把指令切成按需加载的 skill](on-demand-skill-loading.md)。
4. **删掉不适用的条目,而不是留着**。留一条你不打算执行的检查,下次 agent 报告「已完成」时你就没法判断它是真做了还是跳过了。

## 适用边界

*(本节为本仓库补充,原推未讨论)*

- **skill 不等于门禁。** 这批文件是**给模型读的说明**,不是硬性检查。模型可以声称自己跑完了 `pre-push-checks` 而实际没跑。真正的停止判据必须是**一条命令的退出码**——这一点见[把外层循环交出去之前,先补上三样东西](outer-loop-three-parts.md)。把 skill 当成「怎么做」的指引,把 checker 当成「做没做成」的裁判,两者不能互相替代。
- **别把「一线团队在用」当成「适合你」。** 这些流程是为一个高频提交、多人协作、有文档站的开源仓库设计的。团队规模和提交频率差一个量级时,同一套检查会从「防错」变成「拖慢」。
- **发布时它还是 developer preview。** 仓库自己在 README 里用大写警告会有破坏性变更,skill 的组织方式和文件格式随时可能变。**当参考读物用,别做成对上游路径的依赖**(比如写脚本定期拉取)。
- **许可与署名**:仓库是 MIT,改用没问题,但如果你把改写后的版本再发布出去,**保留版权声明是 MIT 的硬条件**。内部自用不涉及这一步。
- **这条实践的可迁移性大于这批文件本身。** 半年后这 11 个 skill 可能已经过时,但「去成熟项目的仓库里翻 `.agents/` `.claude/` `AGENTS.md` 这类目录」这个动作不会过时——**现在越来越多项目把 agent 配置和工程约定一起提交进仓库,那是公开的、免费的、被真实使用验证过的方法论**。

## 一句话

**你需要的工程规范,大概率已经有人写好并开源了——去仓库里翻 agent 配置目录,读懂再改写,比自己从零列清单快一个量级;但记住 skill 只负责「怎么做」,「做没做成」仍然得由退出码说了算。**
