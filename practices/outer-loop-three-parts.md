# 把外层循环交出去之前,先补上三样东西

> **出处** — [@DailyDoseOfDS_](https://x.com/DailyDoseOfDS_/status/2086022123815149692) · 采集于 2026-08-09
> **原作者说法**:agent 的内层循环(模型跑 → 请求工具 → 结果回上下文 → 再跑)是 2022 年 ReAct 就解决了的东西,今年真正被自动化的是**坐在外层的你**——写 prompt、读几轮、再写下一个 prompt。要把外层也交出去,必须补齐三样:真实的停止判据、上下文修剪策略、独立的检查者。缺一个,长循环就会既烧钱又骗你。
> 以下「为什么会骗你」之后的小节多为本仓库补充的工程化落地,非原作者内容。

## 先分清哪一层在动

| | 内层循环 | 外层循环 |
|---|---|---|
| 谁在转 | 模型 ↔ 工具 | 你 ↔ agent |
| 一轮是什么 | 一次工具调用与回填 | 一次「读结果 → 写下一个 prompt」 |
| 谁决定停 | 模型不再请求工具 | 你觉得可以了 |
| 已解决? | 是,框架都长一个样 | 正在被自动化 |

看清这张表才能看懂当下这波「自主 agent / goal 模式 / 长时任务」到底改了什么:**内层没变,变的是把你从外层拿掉。**

而你坐在外层时,是同时在干四件事:决定何时停、持有项目记忆、当审阅者、以及在跑偏时随手打断。**把你拿掉,这四件事不会自动消失,它们必须在系统里各自有个去处。**没安排去处就跑长循环,就是原推说的「烧钱且骗你」。

## 为什么会骗你

三种失效各自对应一样缺失,症状很好认:

| 缺失 | 典型症状 |
|---|---|
| 停止判据不真 | agent 宣布「已完成」,而测试还红着 |
| 不修剪上下文 | 前几轮很聪明,越到后面越笨、越绕、越重复 |
| 检查者是它自己 | 每一轮都「通过」,产出却在原地打转 |

第三条最隐蔽:**让写代码的 agent 判断自己写完没有,它一定说写完了。** 这不是模型不诚实,是它没有别的信号可用。

## 一:停止判据必须是真检查

### 判据不能是它自己能写的字符串

这是最容易踩、也最致命的一个坑。

很多人(包括我)会把验收合约写成一份清单文件,每条带一个 `passes: true/false`,循环的完成条件写成「所有 `passes` 为 true」。看起来很严谨,实际上——**`passes` 是文件里的一个字符串,而 agent 有写文件的权限**。停止判据于是可以被一次编辑直接满足,不需要真的把活干完。

正确的形态是:**`passes` 的真值来自一个外部 checker 的退出码,文件里的那个布尔值只是缓存与展示。**

```
# 错:完成条件 = 文件里全是 true(agent 可以直接改)
# 对:完成条件 = 这条命令 exits 0(agent 改不了退出码)
python3 check_eval.py --all
```

checker 自己去跑测试、探测产物、比对状态,然后**由 checker 回写**那份清单。agent 只负责让检查通过,不负责宣布检查通过。

### 不可自动判定的条目,不能计入停止条件

清单里总有几条是「打开页面看一眼」「人工确认交互手感」这类无法脚本化的。把它们和自动判据混在一起,后果是:**它们只能靠 agent 自述通过,于是整份合约的可信度被拉到最弱那条的水平。**

处理办法是分成两栏:

- **闸门栏(gate)**:全部可由命令判定,循环的完成条件只看这一栏。
- **人工验收栏(human)**:循环**既不能翻它们、也不会因它们卡住**,跑完后作为清单交给人。

清单从「64 条里有 33 条靠自述」变成「31 条硬判据 + 33 条待人工过目」,后者不再污染前者。

### 必须有硬上限

轮数上限、token 上限,写进完成条件本身,而不是靠盯着。

```
完成条件:`python3 check_eval.py --all` exits 0,或达到 N 轮后停止并汇报。
```

后半句不是投降,是**让「没做完」成为一个可被观察的结果**,而不是一场无声的持续扣费。

## 二:上下文修剪——别让合约本身撑爆上下文

原推给的四条(留摘要而非全量历史、大输出落文件、子任务拆独立会话、注意每轮重发整个上下文的成本)都对,但在「有验收合约的循环」里还有一条更具体的:

**别把整份合约每轮都读进去。**

一份写细了的验收合约很容易到几百行(每条都有断言、验证方式、期望输出)。循环跑二十轮,它就被完整重读二十遍——而其中绝大多数条目**早就通过了、这一轮根本不会碰**。

做法是把状态从合约里外置出来,由 checker 生成:

```json
{
  "round": 7,
  "total": 31,
  "passing": 28,
  "failing": ["E4-subtitle-stream", "E6-e2e-playback", "E7-report"],
  "streak": { "E4-subtitle-stream": 3, "E6-e2e-playback": 1, "E7-report": 1 },
  "blocked": []
}
```

每轮进上下文的是这个几十字节的 JSON,加上**当轮要攻的那 1–3 条**的全文。合约全文只在开工与收尾时各读一次。

顺带解释了一个常见困惑:**为什么循环跑到后面反而更笨。** 不只是历史变长——是**信噪比在掉**。二十轮之后,上下文里 90% 是已经通过的条目和早就无关的旧轮次,真正相关的三条被埋在里面。

## 三:独立检查者——两道,不是一道

「换个模型来评」通常被理解成一件事,实际应该是两道不同性质的闸:

| | 第一道 | 第二道 |
|---|---|---|
| 是谁 | 确定性 checker(脚本 / 测试 / 探测命令) | 另一家供应商的模型 |
| 判什么 | 做完没有 | 做对没有 |
| 输出 | 退出码 | 结构化判定 |
| 能否被说服 | 不能 | 能——所以要限制它的输入 |

**第一道不可省。** 它是唯一一个无法被说服的信号,也是「agent 说完成了」与「真的完成了」之间唯一的物理隔离。

**第二道解决第一道判不了的事**:代码能跑通不代表实现对了需求;文档生成了不代表内容没编。这道闸的具体做法(评审方只拿产物 + 原始素材、不给它生成方的推理过程、判据固定不可改)见[异构终审闸门](cross-vendor-judge-gate.md)——两篇讲的是同一件事的两半:**这篇讲为什么必须有个外部信号,那篇讲这个外部信号本身怎么才不被污染。**

## 补一条原推没说的:收敛护栏

三样都补齐了,循环仍然可能跑很多轮才到目标,甚至永远到不了——因为**「有真检查」只保证它不会假装完成,不保证它在前进。**

长循环卡住的实际形态,几乎总是同一个:**在同一条判据上反复试同一类修法**。它每轮都诚实地失败,然后诚实地再试一次。

所以还需要两条基于状态的规则,而它们恰好只依赖上面那份 JSON:

**单调性检查**——记录每轮的 `failing` 数量。连续两轮没有下降,说明当前策略无效,**强制换目标条目**,而不是接着磨。

**卡死升级**——`streak`(同一条连续失败次数)达到 3,把它标成 `blocked`,移出本轮目标,把现象与已试过的修法写进阻塞清单,继续攻别的。**当剩余未通过条目全部 blocked,循环立刻退出并汇报**,而不是继续烧到轮数上限。

这两条把「循环跑不完」从一种消耗,变成一份可读的产出:它会告诉你**卡在哪三条、每条试过什么、为什么过不去**。这通常比它真跑完更有用——因为卡住的地方往往是需求本身没想清楚,而那是你的活,不是它的。

## 适用边界

- **短任务不需要这套。** 三五轮能结束的活,你自己坐在外层就是最便宜的检查者。这套东西的成本(写 checker、维护状态、加护栏)只有在循环要跑几十轮、无人值守时才回本。
- **checker 写不出来,通常说明验收标准还没想清楚。** 这时候该停下来补需求,而不是先跑起来再说——写不出判据的循环,跑多少轮都不会收敛。
- **第二道闸对共模故障无效。** 两个模型读的是同一份错的输入时,它们会一起错。见异构终审闸门那篇的同一条提醒。
- **原推的成本提醒值得重复**:每轮都要重发整个上下文,长循环的花费是单次 prompt 的很多倍。上面的修剪与护栏,一半是为了正确性,一半就是为了这个。
