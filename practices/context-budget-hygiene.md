> **原作者说法**:Claude Code 默认状态是「臃肿」的——费词元、爱争辩、慢。修法不是换模型,而是**把上下文窗口当成一份有限预算来经营**:先用工具量出来谁在占位置,再逐项削减,最后靠会话纪律维持。原推给了十几条具体做法,下面按「量 → 砍 → 维持」重排,并补上边界。
> 个人经验,未经官方确认。文中的命令与配置项以你所用版本的实际约定为准。

## 为什么顺序是「先量再砍」

*(本节为本仓库补充)*

绝大多数「Claude Code 变笨了」的抱怨,处理方式是直接去改提示词。但提示词只是窗口里的一小块——**在你打第一个字之前,窗口就已经被系统提示、工具定义、记忆文件、skill 描述填掉了一部分**。不先量,砍下去的往往是最无关的那块。

原作者给的两条测量入口很关键,它们回答的是两个不同的问题:

| 工具 | 回答的问题 |
|---|---|
| 在**全新会话**里跑 `/context` | 我还没说话,窗口里已经有什么?系统提示、工具、记忆文件、skill 各占多少? |
| `/usage` | 是哪个 MCP server / skill / agent / plugin 在烧我的词元? |

用法是迭代式的:**看一眼 → 删掉最大的那一项 → 重启 → 再看一眼。** 一轮砍一项,否则你不知道是哪一刀起的作用。

## 砍:五个位置

### 1. 全局指令文件控制在 200 行以内

原作者的两条规则:

- **上限 200 行**,只放刚好够用的上下文。**文件越长,被忽略的比例越高。**
- **每 2–3 个月删掉重建一次**,而不是持续往上加。

第二条是这份实践里最反直觉、也最容易被跳过的一条。长期只增不减的指令文件会累积大量「当时为了绕开某个问题写的临时规则」,而那个问题可能早就不存在了。推倒重来的成本远低于逐条审计。

### 2. 「绝对不要做 X」写成权限设置,不要写成句子

> 原作者原话:把 never-do 规则写成 permission settings,**不要**写成指令文件里的句子——**长会话里那些句子会被忽略。**

这条的分量比看上去重:它把一类约束从「模型每次都要记得遵守」降级成「机制上做不到」。凡是能表达成权限、钩子、白名单的禁令,都不该靠自然语言反复叮嘱。

### 3. 能用 CLI 就别用 MCP

> 原作者原话:**一条命令只返回你要的那几行,而一个 MCP 每一次都把它的完整结果倒进窗口。**

这是原推里信息密度最高的一句。同一件事(查数据、读接口、拉列表),走命令行你可以用管道和参数把输出裁到几行;走 MCP 则往往是整个结构化结果进窗口,而且**每次调用都进一次**。

### 4. 关掉不用的 MCP,把少用的 skill 标成手动

- 不用的 MCP server:关掉即可,配置还留在那里,以后要用再开。
- 很少用的 skill:标成**仅手动调用**(原推给的是 `disable-model-invocation: true`),**这样它在你主动喊之前不占任何成本**。

这一条和[把指令切成按需加载的 skill](on-demand-skill-loading.md) 是同一个思路的两面:那篇讲怎么把内容切开,这条讲切开之后**连描述行本身也要控制数量**。skill 切得越碎,常驻的描述行加起来就越可观。

### 5. 推理强度只在规划时开高

> 原作者原话:high effort 只用于规划,其余一律 medium 或 low。

## 工具也要分阶段暴露

*(本节来自第三位作者,见上方补充出处;编排与边界为本仓库补充)*

上面第 3、4 条处理的是**工具占多少上下文**,这一条处理的是另一件事:**同时摆在模型面前的工具有多少个,会直接改变它的行为质量。**

第三位作者在同一个模型、同一套题上做的对比:

- 默认一次性挂满 **25 个工具** → 得分 **91**
- **第一轮只暴露 2 个工具,等它真正开始动手之后再解锁全部** → 得分 **98/99**

他给的解释是:模型的行为只有「规划」和「执行」两个稳定档位,中间是乱流区;一上来把全部能力摊开,它会卡在「先想清楚还是先动手」之间反复横跳。类比是**新员工第一天就开通全公司权限**。

可照做的形式:

- 会话开场只留检索/读取类工具,产出计划;计划确认后再挂上写入、执行、部署类工具。
- 如果你的工具是按 skill / MCP 分组的,这一条正好和「把少用的标成手动」叠加使用:**默认手动,进入执行阶段再打开。**

## 维持:三条会话纪律

- **到达一个检查点、或上下文超过 40 万,就 `/clear`。** 别等到明显变笨了才清。
- **把上下文用量表放进状态栏**(`/statusline`),这样你能**在质量下降之前**看到窗口在变满,而不是事后回溯。
- **重活外包给子代理**:让它们在自己的窗口里做大量阅读,你的主会话只收摘要。视觉任务和计算机操作类任务交给无头 worker,别占主会话。

## 反过来:什么时候该把预算调大

*(本节来自第四位作者,见上方补充出处;这是本文唯一一条**官方口径** —— 发帖者是该编码工具的负责人。编排与边界为本仓库补充)*

本文到这里全在讲怎么少花。但预算管理不等于一味紧缩,所以需要一条对称的做法:**在什么条件下,把窗口调大是对的。**

工具默认的上下文上限,通常**不等于**模型本身支持的上限。以这次的例子:模型文档标称约 105 万词元的窗口,而工具默认把它压在更低的位置。官方给的打开方式是改配置文件顶层的三个键:

| 配置项 | 作用 |
|---|---|
| 模型名 | 选一个**确实支持**长窗口的模型——这是前提,不是可选项 |
| 上下文窗口上限 | 设成你要的预算,例如 100 万 |
| 自动压缩触发阈值 | 设在上限之下留出余量,例如 90 万 |

两个细节值得照抄:

- **这些键必须放在文件顶层,在任何 `[section]` 小节之前**;放错位置会被当成某个小节的配置而不生效。
- **压缩阈值要留头寸**(例中是上限的 90%)。压缩本身要消耗窗口来做,顶到满才触发就没有余地了。

想试而不改默认值,官方同时给了**单次会话**的命令行写法:用 `-m` 指定模型、用 `-c 键=值` 临时覆盖那两个数字,退出即恢复。**任何涉及全局默认值的调整,都该先用这种一次性形式验一轮。**

### 为什么这条不与前面矛盾

原帖最后一句是整条实践里最重要的部分,而且很容易被当客套话读过去:**「默认值是我们仔细调过的」** —— 调的依据是**性能与成本**两件事。也就是说,把窗口开大不是解锁了一个被藏起来的免费档位,而是**你主动把权衡点从「快且便宜」挪到了「记得多」**。

所以这条和本文前半部分不冲突,它们说的是同一句话的两半:

- **砍**,是让同样的预算装下更多有效信息;
- **调大**,是承认某些任务的有效信息本来就装不下,愿意为此付更慢、更贵的代价。

顺序不能反。**先把窗口里的垃圾清掉,再决定要不要买更大的窗口** —— 反过来做,你只是用更贵的价格喂同一批噪音。

## 不清空也能瘦:同一会话里的就地清理

*(本节来自第五位作者,见上方补充出处;编排与边界为本仓库补充)*

前面的会话纪律给的是二选一:要么继续攒,要么清空重来。第五位作者补上了中间那一档 —— **不结束会话,让模型原地把窗口里的垃圾清掉,再用一份精简摘要接着往下跑。**

触发时机是任务跑到中途、上下文开始变杂时,手动发一条指令,要求它:

1. **删除或标记**已废弃的方案、已完成且不需要再参考的内容、与当前目标无关的历史记录、低价值的重复输出;
2. **重新生成一份精简任务摘要**,只保留六项:当前目标、核心约束、已确认决策、当前进度、未解决问题、下一步计划;
3. **声明此后以最新摘要为准**,不再依赖已失效的信息。

第三步是这条做法真正的机关。前两步只是把内容压短,而「以最新摘要为准」是在给模型换锚点 —— 没有这句,它仍然会回头引用那些你刚标成废弃的尝试。

作者给的收益是无效词元消耗减少约 85%(自述,未核实)。但更值得记的是他给的因果:**长对话里堆积的失败尝试和调试日志不只是占位置,它们会把模型往已经否掉的路径上带回去。** 这和「窗口越长、中段利用率越低」是同一现象的两种说法 —— 垃圾不是中性的,它有方向。

与前后两节的关系:

| 做法 | 会话是否继续 | 保留了什么 |
|---|---|---|
| 就地清理(本节) | 继续 | 六要素摘要;原历史被声明为失效 |
| 清空重来 | 中断 | 什么都不留 |
| 交接文档(下一节) | 中断,另起一个 | 一份专为下一个会话写的文档 |

**先试就地清理,撑不住再交接,最后才是清空** —— 三者的代价依次上升。

## 窗口用满之后:交接文档接力

*(本节来自第二位作者,见上方补充出处;编排与边界为本仓库补充)*

上面那条会话纪律——「到检查点或上下文过大就 `/clear`」——处理的是**丢弃**。但长任务并不总能在检查点上被切开,清掉窗口往往连着把「我们试过什么、为什么放弃」一起清掉了。第二位作者给的补法是把清空换成**交接**:

- **设一个触发线,而不是等它满。** 他的做法是把命令做成一个自定义的 `/handoff`:**上下文到 10 万左右就触发**,让模型先产出一份交接文档,下一个会话读这份文档自动续上。
- **交接物是文档,不是对话历史。** 关键在于让模型自己写「下一个我需要知道什么」——这一步是压缩,也是一次强制复盘。
- **配套两条同源做法**:① 用 `AGENTS.md` 自动加载固定的那几个 skill,而不是每轮手挂;② **开工前先让 agent 拿上百个问题把你盘问一遍**,把决策提前到动手之前。
- **作者自己的评价是「这确实很费决策」**,但他认为判断力和品味目前仍是最强的一环,值得把人的时间花在这里。

和本文前半部分的关系:**砍是让窗口撑得更久,交接是承认它终究撑不住。** 两者不冲突——先靠削减把交接的频率降下来,再靠交接让「必须清空」不再等于「重新开始」。

## 顺序也算钱:让不变的东西留在缓存里

*(本节来自第六位作者,见上方补充出处;编排与边界为本仓库补充)*

前面所有小节处理的都是**窗口里放多少**。这一节处理的是一个正交的问题:**同样的内容,摆放顺序不同,价钱不同。**

供应商侧的提示词缓存基本都按**前缀**匹配——命中与否取决于「从第一个词元开始,有多长的一段和上次完全一致」。一旦前面某处发生变动,**它后面的全部内容都要重新计费、重新计算**,哪怕那部分一个字没改。所以这条做法只有一句话:

> **不变的放前面,易变的放后面。**

具体到日常:

| 放在前面(整轮不动) | 放在后面(每轮都变) |
|---|---|
| 项目规则、`AGENTS.md` / 全局指令文件 | 本轮的具体需求 |
| 开发规范、代码约定 | 刚粘进来的报错、日志片段 |
| 长期不动的系统提示 | 临时补充的上下文 |

原作者同时给了一条容易被当成废话的配套要求:**保持项目配置稳定**——别频繁切模型、切工作目录、改工具配置和开发规则。理由是同一个:**这些东西都在前缀里**,换一个模型或多挂一个 MCP,前缀就变了,之前攒下的缓存整段作废。

### 和前面各节的关系

这条与「砍」不冲突,但优化的是**不同的指标**:

- **砍**降低的是窗口占用与注意力稀释——治的是「模型变笨」;
- **顺序**降低的是重复计算与费用/延迟——治的是「同样的活越跑越贵、越跑越慢」。

两者偶尔会打架:为了让缓存稳定,你会倾向于把那份全局指令文件**原样固定在最前面不动**;而「砍」那一节要求你**每 2–3 个月推倒重建它**。调和方式是把重建当成一次**有计划的缓存失效**——集中改一次,而不是每天顺手加两行。**零散的小修改是缓存最贵的敌人。**

## 把 Agent 账单拆成六个可测环节

*(本节来自第七位作者,见上方补充出处;结构与边界为本仓库补充)*

前面的做法大多盯着「窗口里有多少东西」。这位作者把视角再往外推了一层:**一次 Agent 任务的总成本,是模型、Context、缓存、工具定义、工具往返和检索路径共同产生的。** 只换一个便宜模型,常常只是动了账单里的一行。

他给出六组「改之前 → 改之后」,可以直接变成一轮成本审计:

| 环节 | 默认做法 | 可测的替代方案 |
|---|---|---|
| 模型路由 | 所有任务都用最强模型 | 主 Agent 保留强模型;子代理先降级,再用固定 benchmark 决定哪些任务必须升级 |
| Context | 窗口能装多少就塞多少 | 在质量明显下降前主动 compact;推理强度默认中档,只对高难环节提升 |
| 重复历史 | 每轮重读同一批前缀 | 对稳定前缀使用 Prompt Cache,并按交互会话与短命子代理设置不同 TTL |
| 工具定义 | 启动时加载全部 MCP/工具 | 用 Tool Search 或 CLI 按需暴露,让未使用工具不进入本轮上下文 |
| 工具往返 | Agent 一步一步轮询和调工具 | 把轮询、分页和多次调用收进一个 Code Mode 脚本,只把最终结果送回模型 |
| 代码库检索 | 每次从全库重新搜索 | 预先构建 Context Graph 或等价索引,把开放式搜索变成有结构的查询 |

最后补一块不能省的仪表盘:**在终端显示当前 Session 的实时成本,并用 Session Analyzer 找出浪费发生在哪一环。** 没有分项账单,动态路由和缓存只能靠感觉调;看见总金额也无法回答「该砍哪一刀」。

### 怎么跑一轮对照

*(以下为本仓库补充)*

1. 选 10–30 个重复出现、能自动判定成功与否的真实任务,固定输入、数据快照和 checker。
2. 记录基线的成功率、总 Token、缓存命中、工具调用次数、墙钟时间与费用;不要只看总 Token。
3. 每次只改一个环节,先从按需工具或子代理降级开始;否则省下来的成本无法归因。
4. 只有在成功率不下降、尾部时延可接受时才保留改动。低价但重跑两次的路线可能更贵。
5. 把保留下来的路由规则写成可版本化配置,定期用同一组任务回归;模型和定价变化后重新测。

作者转述的 Uber 案例给了几个醒目的数字:100+ 工具直接加载会带入约 5 万–7 万 Token;Code Mode 在其 SQL 测试中节省 50% 以上 Token,大批量工作流超过 90%;带 Graph Grounding 的一个案例 38 秒答对,无 Grounding 运行 20 分钟仍错误。**这些是二手案例数字,没有在本轮独立复现,只能用来决定先测哪里,不能直接当成本承诺。**

## 适用边界

*(本节为本仓库补充,原推未讨论)*

- **「越长越被忽略」是经验判断,不是可复现的实验结论。** 200 行是原作者的手感阈值,不同模型、不同版本的实际衰减点不一样。把它当成「该定期审一遍」的提醒,而不是一个需要严格卡的数字。
- **让模型「只说必要的话」有明确代价。** 原推建议在全局文件里加一条要求模型用简化技术英语、只报做决策所需信息的指令。这在你熟悉的代码库上是净收益;但**当你正在摸一个陌生系统、需要模型解释它看到了什么时,这条会让你损失掉最有价值的部分**。按场景开关,别设成永久全局。
- **「CLI 优于 MCP」有前提**:命令行工具的输出你得能裁。遇到那种只会吐一大坨 JSON、没有筛选参数的 CLI,它并不比 MCP 省;真正省的是「你能精确控制返回什么」这件事本身。
- **手动化 skill 会牺牲召回。** 标成仅手动之后,模型不会在你没想到的时候提醒你「这里应该用那套流程」。**对你自己都记不住的流程,这个代价可能比省下的上下文更贵。**
- **定期推倒重建指令文件有风险**:里面可能混着几条来之不易的踩坑规则。重建前先把「为什么有这条」写清楚,否则你会在三个月后重新踩一遍同一个坑。
- 原推提到的具体命令、配置项与开关名**因工具版本而异**,落地时以你手上版本的文档为准。
- **交接文档会撒谎,而且是自信地撒谎。** 让模型总结「我们试过什么」时,它可能把没验证过的推断写成已确认的结论,下一个会话读到后会当前提用。**交接文档里凡是「已经排除 / 已经确认」的句子,值得你自己扫一眼**——这是整套做法里唯一无法自动化掉的一步。
- **触发线是个手感值,不是安全线。** 10 万这个数只对特定窗口大小和任务粒度成立。真正的判断依据是「产出这份交接文档本身还有没有余量」:太晚触发时,模型连总结都写不完整。
- **把窗口调大不会提升「有效上下文」,只会提升「可容纳上下文」。** 长窗口下模型对中段内容的利用率普遍下降,是被反复观察到的现象。**如果你调大之后感觉更好用了,先怀疑是不是原本就该砍的东西现在被容忍了** —— 那属于把问题推迟,不是解决。
- **改默认值之前先用单次会话验。** 官方那条做法里附带的一次性命令行写法不是便利功能,而是安全阀:上下文上限和压缩阈值这类数字,改错了不会报错,只会让会话在某个不确定的时刻表现异常。
- **压缩阈值和上限要一起改,不能只动一个。** 只把上限拉高、压缩阈值仍停在旧位置,等于自愿在远未用满时就开始丢历史;反过来只把阈值抬高而上限没动,则可能压根来不及压缩。
- **就地清理是有损压缩,而且由模型自己决定损哪一部分。** 它判断「已废弃」的依据是对话表面,而你可能因为别的原因还需要那一段。**对需要回溯早期细节的任务(排查一个跨越多轮的 bug、复盘当初为什么选 A 不选 B),这条做法的风险大于收益。**
- **清理完先扫一眼摘要再往下跑。** 六要素里最容易丢的是「核心约束」—— 那些你在第三轮随口追加的限制条件,模型压缩时未必认为重要。**丢了约束的摘要比不清理更危险,因为它看起来很干净。**
- **别把它做成定时动作。** 清理本身要花一次完整的读写,窗口还干净时触发纯属浪费;真正的触发信号是「你发现它开始重复提已经否掉的方案」。
- **缓存有存活时间,隔夜不算数。** 前缀缓存通常只在分钟级到小时级的窗口内有效,过期后第一次请求照样全价。**它优化的是「连续工作的一小时」,不是「这个项目从此便宜了」。**
- **别为了凑缓存把该删的东西留着。** 「不变的放前面」很容易被读成「前面的东西不要动」,进而变成不敢清理陈旧规则的借口。**缓存省的是钱,臃肿赔的是判断力**——冲突时后者优先。
- **动态路由必须先有任务级 benchmark。** 没有固定输入和 checker 时,「子代理默认降级」只是把质量问题藏到下游;一旦需要主 Agent 重做,账单可能更高。
- **Context Graph 不是免费索引。** 构建、更新和权限过滤本身要花成本;代码变化快、任务很少或仓库很小时,直接搜索可能更便宜、更准确。
- **Code Mode 会把多次工具动作藏进一段程序。** 它减少模型往返,也可能降低逐步审批和可观测性。涉及付款、删除、发布或生产变更时,不要为了省 Token 把每一步授权折叠掉。
- **缓存 TTL 是供应商和产品实现细节。** 作者给出的 1 小时与 5 分钟只是其工作流选择,不是通用默认值;命中率、价格和过期策略都要从实际账单验证。
- **原推给的收益数字(省 80% 无效词元、效率提升 70%)是自述,未核实**,且高度依赖具体工作流:一个每轮都要粘贴新日志的任务,前缀命中率天然就低,做这些排序也拿不到那个量级的收益。
- **「上百个问题的盘问」不适合所有任务。** 它在需求含糊、代价高的任务上是净收益;在你已经清楚要什么的小改动上,它只是把成本从执行挪到了问答。作者自己也说这很费决策——**这句话是边界,不是谦辞**。

## 一句话

**上下文不是越大越好用,它是一份需要主动经营的预算——先量出来谁在占位置,再一次砍一项,最后靠会话纪律守住。**
