> **原作者说法**:Claude Code 默认状态是「臃肿」的——费词元、爱争辩、慢。修法不是换模型,而是**把上下文窗口当成一份有限预算来经营**:先用工具量出来谁在占位置,再逐项削减,最后靠会话纪律维持。原推给了十几条具体做法,下面按「量 → 砍 → 维持」重排,并补上边界。
> 个人经验,未经官方确认。文中的命令与配置项以你所用版本的实际约定为准。

## 为什么顺序是「先量再砍」

*(本节为本仓库补充)*

绝大多数「Claude Code 变笨了」的抱怨,处理方式是直接去改提示词。但提示词只是窗口里的一小块——**在你打第一个字之前,窗口就已经被系统提示、工具定义、记忆文件、skill 描述填掉了一部分**。不先量,砍下去的往往是最无关的那块。

原作者给的两条测量入口很关键,它们回答的是两个不同的问题:

| 工具 | 回答的问题 |
|---|---|
| 在**全新会话**里跑 `/context` | 我还没说话,窗口里已经有什么?系统提示、工具、记忆文件、skill 各占多少? |
| `/usage` | 是哪个 MCP server / skill / agent / plugin 在烧我的词元? |

用法是迭代式的:**看一眼 → 删掉最大的那一项 → 重启 → 再看一眼。** 一轮砍一项,否则你不知道是哪一刀起的作用。

## 砍:五个位置

### 1. 全局指令文件控制在 200 行以内

原作者的两条规则:

- **上限 200 行**,只放刚好够用的上下文。**文件越长,被忽略的比例越高。**
- **每 2–3 个月删掉重建一次**,而不是持续往上加。

第二条是这份实践里最反直觉、也最容易被跳过的一条。长期只增不减的指令文件会累积大量「当时为了绕开某个问题写的临时规则」,而那个问题可能早就不存在了。推倒重来的成本远低于逐条审计。

### 2. 「绝对不要做 X」写成权限设置,不要写成句子

> 原作者原话:把 never-do 规则写成 permission settings,**不要**写成指令文件里的句子——**长会话里那些句子会被忽略。**

这条的分量比看上去重:它把一类约束从「模型每次都要记得遵守」降级成「机制上做不到」。凡是能表达成权限、钩子、白名单的禁令,都不该靠自然语言反复叮嘱。

### 3. 能用 CLI 就别用 MCP

> 原作者原话:**一条命令只返回你要的那几行,而一个 MCP 每一次都把它的完整结果倒进窗口。**

这是原推里信息密度最高的一句。同一件事(查数据、读接口、拉列表),走命令行你可以用管道和参数把输出裁到几行;走 MCP 则往往是整个结构化结果进窗口,而且**每次调用都进一次**。

### 4. 关掉不用的 MCP,把少用的 skill 标成手动

- 不用的 MCP server:关掉即可,配置还留在那里,以后要用再开。
- 很少用的 skill:标成**仅手动调用**(原推给的是 `disable-model-invocation: true`),**这样它在你主动喊之前不占任何成本**。

这一条和[把指令切成按需加载的 skill](on-demand-skill-loading.md) 是同一个思路的两面:那篇讲怎么把内容切开,这条讲切开之后**连描述行本身也要控制数量**。skill 切得越碎,常驻的描述行加起来就越可观。

### 5. 推理强度只在规划时开高

> 原作者原话:high effort 只用于规划,其余一律 medium 或 low。

## 工具也要分阶段暴露

*(本节来自第三位作者,见上方补充出处;编排与边界为本仓库补充)*

上面第 3、4 条处理的是**工具占多少上下文**,这一条处理的是另一件事:**同时摆在模型面前的工具有多少个,会直接改变它的行为质量。**

第三位作者在同一个模型、同一套题上做的对比:

- 默认一次性挂满 **25 个工具** → 得分 **91**
- **第一轮只暴露 2 个工具,等它真正开始动手之后再解锁全部** → 得分 **98/99**

他给的解释是:模型的行为只有「规划」和「执行」两个稳定档位,中间是乱流区;一上来把全部能力摊开,它会卡在「先想清楚还是先动手」之间反复横跳。类比是**新员工第一天就开通全公司权限**。

可照做的形式:

- 会话开场只留检索/读取类工具,产出计划;计划确认后再挂上写入、执行、部署类工具。
- 如果你的工具是按 skill / MCP 分组的,这一条正好和「把少用的标成手动」叠加使用:**默认手动,进入执行阶段再打开。**

## 维持:三条会话纪律

- **到达一个检查点、或上下文超过 40 万,就 `/clear`。** 别等到明显变笨了才清。
- **把上下文用量表放进状态栏**(`/statusline`),这样你能**在质量下降之前**看到窗口在变满,而不是事后回溯。
- **重活外包给子代理**:让它们在自己的窗口里做大量阅读,你的主会话只收摘要。视觉任务和计算机操作类任务交给无头 worker,别占主会话。

## 窗口用满之后:交接文档接力

*(本节来自第二位作者,见上方补充出处;编排与边界为本仓库补充)*

上面那条会话纪律——「到检查点或上下文过大就 `/clear`」——处理的是**丢弃**。但长任务并不总能在检查点上被切开,清掉窗口往往连着把「我们试过什么、为什么放弃」一起清掉了。第二位作者给的补法是把清空换成**交接**:

- **设一个触发线,而不是等它满。** 他的做法是把命令做成一个自定义的 `/handoff`:**上下文到 10 万左右就触发**,让模型先产出一份交接文档,下一个会话读这份文档自动续上。
- **交接物是文档,不是对话历史。** 关键在于让模型自己写「下一个我需要知道什么」——这一步是压缩,也是一次强制复盘。
- **配套两条同源做法**:① 用 `AGENTS.md` 自动加载固定的那几个 skill,而不是每轮手挂;② **开工前先让 agent 拿上百个问题把你盘问一遍**,把决策提前到动手之前。
- **作者自己的评价是「这确实很费决策」**,但他认为判断力和品味目前仍是最强的一环,值得把人的时间花在这里。

和本文前半部分的关系:**砍是让窗口撑得更久,交接是承认它终究撑不住。** 两者不冲突——先靠削减把交接的频率降下来,再靠交接让「必须清空」不再等于「重新开始」。

## 适用边界

*(本节为本仓库补充,原推未讨论)*

- **「越长越被忽略」是经验判断,不是可复现的实验结论。** 200 行是原作者的手感阈值,不同模型、不同版本的实际衰减点不一样。把它当成「该定期审一遍」的提醒,而不是一个需要严格卡的数字。
- **让模型「只说必要的话」有明确代价。** 原推建议在全局文件里加一条要求模型用简化技术英语、只报做决策所需信息的指令。这在你熟悉的代码库上是净收益;但**当你正在摸一个陌生系统、需要模型解释它看到了什么时,这条会让你损失掉最有价值的部分**。按场景开关,别设成永久全局。
- **「CLI 优于 MCP」有前提**:命令行工具的输出你得能裁。遇到那种只会吐一大坨 JSON、没有筛选参数的 CLI,它并不比 MCP 省;真正省的是「你能精确控制返回什么」这件事本身。
- **手动化 skill 会牺牲召回。** 标成仅手动之后,模型不会在你没想到的时候提醒你「这里应该用那套流程」。**对你自己都记不住的流程,这个代价可能比省下的上下文更贵。**
- **定期推倒重建指令文件有风险**:里面可能混着几条来之不易的踩坑规则。重建前先把「为什么有这条」写清楚,否则你会在三个月后重新踩一遍同一个坑。
- 原推提到的具体命令、配置项与开关名**因工具版本而异**,落地时以你手上版本的文档为准。
- **交接文档会撒谎,而且是自信地撒谎。** 让模型总结「我们试过什么」时,它可能把没验证过的推断写成已确认的结论,下一个会话读到后会当前提用。**交接文档里凡是「已经排除 / 已经确认」的句子,值得你自己扫一眼**——这是整套做法里唯一无法自动化掉的一步。
- **触发线是个手感值,不是安全线。** 10 万这个数只对特定窗口大小和任务粒度成立。真正的判断依据是「产出这份交接文档本身还有没有余量」:太晚触发时,模型连总结都写不完整。
- **「上百个问题的盘问」不适合所有任务。** 它在需求含糊、代价高的任务上是净收益;在你已经清楚要什么的小改动上,它只是把成本从执行挪到了问答。作者自己也说这很费决策——**这句话是边界,不是谦辞**。

## 一句话

**上下文不是越大越好用,它是一份需要主动经营的预算——先量出来谁在占位置,再一次砍一项,最后靠会话纪律守住。**
